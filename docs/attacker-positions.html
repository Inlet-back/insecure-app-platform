「端末を奪った人」は1つの立場ではありません。 ロック中の端末を拾っただけの人、ロックが解けた端末を触れる人、root を取った人、 バックアップのファイルだけを持っている人では、できることがまるで違います。 カードは肩書ではなく、その相手が実際に持っている能力で切ってあります。

1. 脆弱性より先に、攻撃者を決めます

導入では、隔離があるから攻撃がなくなったのではなく、攻撃の行き先が移っただけだという話をしました。 移った先の4つがそのまま4つの章です。ただし、章を開いた時点で、 どこが破れるかも、使う道具も、成功するかどうかも、こちらが決めてしまっています。

実際の診断では順番が逆になります。先に決めるのは相手です。 Android の設計を書いた The Android Platform Security Model という文書も、 機構の説明より先に、どういう相手をどこまで想定するのかを並べています。 想定する相手が決まっていないと、あとで「この対策は効いていますか」と聞かれたときに答えようがありません。 効くかどうかは、相手によって変わるからです。

導入で決めた「あなたの立場」は、検証者として進むという構えのことでした。 このページで言う立場は別のもので、確かめるときに誰の役をやるかを指します。

ここは作りながら一番遅れて気づいたところです。 4章ぶんを書き終えるまで、教材の中で攻撃者に名前が付いていませんでした。 各章の最後の表には「root を取った」「Frida を入れられる」と書いてあるのに、 それが何者で、どうすればそこに立てるのかは、どこにも書いていなかったのです。

カードの読み方

新しく用意した道具は1つもありません。すでに各章で使っているものに、名前と前提を付けただけです。 カードは3行で固定してあります。3行目のそこに立つには何が要るかを毎回読んでください。 攻撃が現実的かどうかは、だいたいこの行で決まります。

Basicまず3つ

各章の Basic で、すでにこの3つに立っています

APK だけ持っている 端末の外

unzip / apktool / grep

できること
コードと Manifest と同梱リソースを全部読めます。窓口の名前も、直書きした鍵もここで出ます。
できないこと
動いている端末の中の値には、1つも届きません。
立つには
配布されている APK を手に入れるだけです。端末には触りません。

通信路にいる人 端末の外

Burpなどの明示プロキシ / 攻撃者管理AP / 経路上の観測装置

できること
端末の外に出ていくパケットを覗けます。条件が揃えば書き換えもできます。
できないこと
端末の中に置いてあるだけのものには届きません。
立つには
通信を明示プロキシへ向ける、攻撃者管理APを通す、経路上の機器を押さえる。 同じWi-Fiにいるだけでは、この能力を持つとは限りません。

開発者の口 端末の中

adb shell / content query（run-asは教材の観測用途）

できること
shellユーザーとして端末を操作できます。debuggableな教材アプリでは run-as を使って、アプリ自身から見える保存形式を観測できます。
できないこと
run-as が効くのは debuggable なアプリだけです。ストアのリリース版では通りません。
立つには
ユーザーが開発者オプションと USB デバッグを自分で有効にしている必要があります。
初学者はここまでです
残り4枚は、取得済みファイル・攻撃者アプリ・root・Frida を使う層のものです。 先に 環境構築 から 第1章 へ進んでください。 章を通したあと、攻撃面マップでこの3枚を使います。

Standardさらに3つ

攻撃者アプリ（P1〜P7b）と root を触った人向け

同じ端末の普通のアプリ 端末の中

attacker アプリ（P0〜P7b）

できること
公開されている窓口を叩けます。自分の UID で通る操作なら全部できます。
できないこと
他アプリのファイルを直接開けません。別 UID なので所有者が一致しません。
立つには
ユーザーにアプリを1つ入れてもらうだけです。特別な権限は要りません。

アプリのデータファイルだけを手に入れた 端末の外

バックアップの展開 / 吸い出したデータ / adb pull の結果

できること
その時点のファイルの中身を、時間をかけて調べられます。端末は手元になくて構いません。
できないこと
端末の上で何かを実行できません。Keystore に鍵を使わせることも、窓口を叩くこともできません。
立つには
バックアップを手に入れる、吸い出されたデータを受け取る。端末そのものには触れていません。

動いている端末で root を持っている 端末の中

adb root / ファイル直読み / デバッガ / Frida の設置

できること
UID の照合を無視してファイルを読めます。さらに、動いているプロセスを覗き、止め、 コードを注入できます。この最後の1つが、1枚下のカードへの入口です。
できないこと
ファイルが読めることと、中身が読めることは別です。 Android Keystore が管理している鍵のバイト列は、それでも直接は取り出せません。 どこまで耐えるかは端末の保護レベル次第で、 アプリの「鍵がどこにあるか調べる」に出る実測値で決まります。
立つには
root 化済みの端末を使う、ブートローダを開ける、OS の脆弱性を使う。 ロックの解けた端末が手元にあることが前提です。

「端末を奪った」は、これ1枚では表せません

物理的に端末を手に入れただけでは、アプリのデータには届きません。 間に立ちはだかるものが違うので、少なくとも次の4つは別の前提として扱います。

前提そこから何ができるかこの表のどの列か
ロック中の端末を物理的に取得した ほぼ何もできません。画面ロックが解けるまで、ユーザーデータは ファイルベース暗号化で保護されたままです どの列にも立てていません
ロックが解けた端末を操作できる 画面から見えるものは見えます。開発者オプションが有効なら adb shell の列に上がれます adb shell（条件付き）
root / OS を侵害した ファイルを直接読め、プロセスにも入れます。 ただしブートローダのアンロックはデータ消去を伴う構成が多く、 「端末を拾ったからここに立てる」わけではありません root端末（→ プロセス内）
バックアップやファイルのコピーだけを持っている ファイルの中身は調べられますが、端末の上では何も実行できません 取得済みファイル

第1章の暗号化が効くのはいちばん下の行に対してで、 上から3行目に対しては効きません。「端末を奪われても安全です」という一文は、 この4つのどれを指しているのかを言わないと判定できません。

強い順に一直線には並びません

ここまでの6枚は、上から下へ強くなっていくように読めます。ただし、 別アプリ・adb shell・root は使える権限が異なり、対象や操作によって結果も変わります。

一方で、通信路にいる人は端末の中のファイルに一切届きませんし、 root を取った人も、経路を流れる暗号文をそのまま読めるわけではありません。 強さが一直線なら、表は階段状になるはずです。そうならないことを、攻撃面マップで確かめます。

Deep最後の1つ

Frida を入れた人向け。ここは必修ではありません

動いているアプリの中 端末の中

Frida

できること
アプリ自身として振る舞えます。アプリにできることは全部できます。
できないこと
アプリにできないことはできません。権限はアプリのものを超えません。
立つには
この教材では root を取ったエミュレータに frida-server を置きます。 root端末のカードから上がる段として扱っているのは、そのためです。
教材の前提と、技術一般の制約は別です
この教材が root を要求しているのは、手順を1本に固定するためであって、 Frida 一般が root を必要とするからではありません。 非 root の端末でも、次のような経路でプロセス内にコードを持ち込めます。
  • Frida Gadget を組み込んで APK を再パッケージし、自分の鍵で署名し直す
  • android:debuggable="true" のアプリにデバッガとして接続する
どちらも「アプリを配布された形のまま動かす」前提を崩しますが、 root は取っていません。root → Frida が唯一の経路ではありません。 攻撃面マップで root の列を評価するときは、 「root がなければプロセス内に入れない」とは読まないでください。

7つの立場を、入手できるものと必要な条件で並べ直します。

2. この名前をどこで使うか

各章を通したあと、攻撃面マップで、 1つの資産に対してどの立場から届くのかを数えます。表は層ごとに3枚あり、 Basic の表に出てくる立場は、このページの最初の3枚だけです。

そこで数えるのは最終的な到達可能性です。 root のように、直接はできなくても一段進めば届く立場は、 マップでは ◐ として残ります。「直接できないこと」を「できないこと」と書かないでください。
