終章 — この先どこで調べるか

4章で使った考え方を、教材の外へ持ち出すための地図

この章のゴール
新しい脆弱性を覚えることではありません。 教材に載っていない対象に出会ったとき、どこを見て、何を自分で確かめるかを決められることです。

1. 4章を1行ずつに畳む

細かい手順は忘れてかまいません。残すのはこの4行だけです。

章持ち帰る1行
第1章 プロセス境界 アプリ同士を隔てているのはアプリのコードではなく OS なので、 隔離が効く条件も崩れる条件も、OS 側を見に行かないと分かりません
第2章 IPC 境界 ファイルの権限を一切変えなくても、自分で開けた窓口から同じデータは出ていきます。 誰が呼んでいるかを確かめるのは、OS ではなくアプリの仕事です
第3章 ネットワーク境界 HTTPS が読まれるかどうかは暗号の強さではなく、 端末が誰を信じているか（トラストストアの中身）で決まります
第4章 Android Keystoreと鍵の使用 鍵が取り出せないことと、鍵が使われないことは別です。 クライアント側の判定は、クライアントを支配した相手には効きません

2. 4章に共通していた1つの問い

その対策は「何から」守るのか
守れないケースが見つかったとき、それは対策の失敗とは限りません。多くは射程の外にあるだけです。
「安全です」と言う代わりに、どの相手までなら守れるかを言えること。それがこの教材の到達点です。

この問いは、新しい技術に出会っても形を変えません。 生体認証でも、パスキーでも、難読化でも、聞くことは同じ3つです。

  • 攻撃者はどこにいる想定か（ネットワーク上／同じ端末の別アプリ／端末の持ち主／root）
  • その防御を執行しているのは誰か（アプリのコードか、OS か、サーバか、ハードウェアか）
  • 執行者を攻撃者が支配できる場合、その防御はどうなるか

3つ目に「無力になる」という答えが出たなら、それは実装のミスではなく設計上の射程です。 そこまで言い切れるようになれば、AI が出してきた「これで安全です」を、自分の手で検証できます。

3. 調べる先（一次情報）

検索して出てくるブログより、まずこの3つを見てください。どれも無料で、更新され続けています。

OWASP MAS（Mobile Application Security）

名前何が書いてあるかいつ使うか
MASVS
（検証標準）		 モバイルアプリが満たすべき要件の一覧。STORAGE / CRYPTO / AUTH / NETWORK / PLATFORM / CODE / RESILIENCE に分かれている 何を確かめるべきかの目次として。 各章の先頭にあったバッジ（MASVS-STORAGE-1 など）はこの番号です
MASTG
（テストガイド）		 その要件をどう確かめるかの具体的な手順。コマンド付き 手を動かすとき。この教材の各章は、MASTG の手順を 「なぜそうなるか」側に寄せて組み直したものです
MAS Checklist MASVS の要件を確認用リストにしたもの 診断の抜け漏れ確認に

owasp.org/mas/ から3つともたどれます。

Android の公式ドキュメント

「この API は本当は何をしているのか」を確かめる先です。 この教材で触った箇所に対応するページを挙げておきます。

章見るところ
第1章アプリのサンドボックス（Application Sandbox）、データとファイルの保存、 Security library（EncryptedSharedPreferences とその現状）
第2章アプリのコンポーネント、<provider> / <activity> の android:exported、 <permission> の protectionLevel、Binder と AIDL
第3章Network Security Configuration、 cleartextTrafficPermitted、証明書のピン留めに関する注意
第4章Android Keystore システム、KeyGenParameterSpec、 setUserAuthenticationRequired、StrongBox、鍵の attestation、Play Integrity

読み方のコツがひとつあります。 公式ドキュメントは「こう書けば安全です」という書き方をするので、そこで読み終えずに、 その安全を誰が執行しているのかを探しながら読んでください。 執行者がどこにも書かれていない場合、たいていはアプリ自身が執行者になっています。 つまり、アプリを支配されたら終わる種類の防御です。

変化を追う

  • Android Developers の「動作の変更点」：targetSdk を上げると何が変わるか。 exported の明示が必須になった話も、平文通信が既定で禁止になった話もここにあります
  • Android Security Bulletin：毎月の修正一覧。OS 側の守りが更新され続けているのが分かります
  • CWE：脆弱性の型の共通名。診断結果や AI の出力に付いている番号はこれです

4. 次の一歩

この教材のアプリは、確かめ方を身につけるための練習台でした。 同じ6段を教材の外で回せるようになったら卒業です。

  1. 自分が書いたアプリを対象にする。 まず第2章のやり方で Manifest を見て、exported になっているものを数え、 それぞれについて「外から呼ばれても困らないか」を答えてみてください
  2. AI に診断させて、判定する。 自分のコードを AI に見せて指摘を出させ、この教材と同じように 実験で棄却するか採用するかを決めます。これが オラクル演習の実物版です
  3. MASTG から1項目選んで通す。 教材になかったテスト（WebView、ログ出力、バックアップなど）を1つ選び、 ①〜⑥の形に自分で組み直してみてください
やってよい対象の線引き
手を動かしてよいのは、自分が作ったアプリ、自分で用意した検証端末に自分で入れたアプリ、 そして許可が明示されている対象（バグバウンティのスコープなど）だけです。
他人のアプリやサービスに対して同じことをすると、技術的にはまったく同じ操作でも扱いが変わります。 境界にあるのは許可の有無であって、手口の強さではありません。

5. 最後に

この教材で身につけたのは、4つの攻撃手順ではありません。 主張が出てきたときに、それを実験に翻訳して確かめる手つきのほうです。

ツールも AI も、この先もっと賢くなります。 それでも「その出力は本当か」を確かめる人は、まだ必要とされています。
