この章の問い
第1〜3章で見てきた防御は、どれも「アプリのプロセスを取られたらそこで終わり」でした。 では、端末の持ち主自身が敵になる状況で、アプリは何か守れるのでしょうか。 守れるとしたら、それは何をどこまで守っているのでしょうか。
初めての人の最短ルート

この章で触る仕組み

読むだけ・7分。端末の持ち主自身が敵になる場合の話です。

端末にデータを残すとき、ログイン用のトークンやメモのように、そのままでは置きたくないものがあります。 暗号化すれば読めなくなりますが、暗号化には鍵が要り、その鍵もまた端末のどこかに置くことになります。 Android Keystore は、この鍵の置き場所をアプリの外、つまり OS の側で引き受けるための、 ごく普通の仕組みです。端末によっては、その先で OS から隔離された実行環境（TEE）や専用チップ（StrongBox）が使われます。 使われるかどうかは端末次第なので、この章では実測値を表示して確かめます。

仕組みを詳しく読む（図・問答・用語）

Q1. 暗号化すれば読めなくなります。では、鍵はどこに置きますか。

コードに書くか、OS に預けるかの2択です。効いてくるのは置き場所のほうです。

対称鍵暗号は同じ鍵で暗号化と復号をします。速くて扱いやすいのですが、 鍵が漏れた時点で暗号文は読まれます。だから設計で効いてくるのは「どう暗号化するか」よりも 鍵をどこに置くかになります。

どう暗号化するかにも差はあります。ECB は同じ平文が毎回まったく同じ暗号文になるので、 中身が読めなくても「前と同じものを送った」ことが分かってしまいます。 GCM は毎回変わる値（IV）を混ぜるため暗号文も毎回変わり、改竄検知も付きます。 この違いは手順4 で実際に見ます。

Q2. 鍵をアプリの外に置けますか。

置けます。Android Keystore に作らせると、アプリは名前でしか鍵を指せなくなります。

アプリは KeyGenParameterSpec で「AES の鍵を tee_demo_key という名前で、 この条件で使えるように作ってほしい」と頼み、以後はその名前（alias）だけで鍵を指します。 鍵の中身を取りに行く getEncoded() は null を返します。

実際にどこに置かれているかは端末次第です。 OS から隔離された実行環境（TEE）や専用のチップ（StrongBox）かどうかは、 KeyInfo の getSecurityLevel() で分かります。 エミュレータでは SOFTWARE と出るのが普通です。

Q3. 取り出せないなら、もう安全ですか。

言えません。鍵の「保持」と「使用」は別物だからです。

鍵を渡してもらえなくても、「この鍵で復号して」と頼むことはできます。 頼めるのはその鍵を作ったアプリ自身です。 裏を返すと、アプリのプロセスとして動ける相手には、 鍵を見せないまま結果だけを渡すことになります。

だから「何から守るつもりなのか」を決めないと、この問いには答えられません。 この章から持ち帰ってもらいたいのは、正直なところここ1つだけです。

守っているのは誰か：OS（Android Keystore）、端末によってはハードウェア。 ただし、アプリのプロセスそのものを取られた場合に 「鍵を使わせない」ところまでは面倒を見てくれません。

用語だけをもう一度並べる（問答で出たものの一覧。あとで引く用）
対称鍵暗号と、鍵の置き場所
同じ鍵で暗号化と復号をする方式です。速くて扱いやすいので広く使われますが、 鍵が漏れた時点で暗号文は読まれます。だから設計で効いてくるのは「どう暗号化するか」よりも 「鍵をどこに置くか」のほうです。
ECB と GCM
ECB は同じ平文が毎回まったく同じ暗号文になるので、 中身が読めなくても「前と同じものを送った」ことが分かってしまいます。 GCM は毎回変わる値（IV）を混ぜるため暗号文も毎回変わり、改竄検知も付きます。
Android Keystore
鍵を生成して保管する OS の金庫です。アプリは KeyGenParameterSpec で 「AES の鍵を tee_demo_key という名前で、この条件で使えるように作ってほしい」と頼み、 以後はその名前（alias）だけで鍵を指します。アプリは鍵の中身を取り出せません。 できるのは「この鍵で暗号化して」と OS に頼むことだけです。
鍵の「保持」と「使用」は別物
取り出せないことと、使えないことは別です。この区別がこの章の核心になります。
セキュリティレベル（SOFTWARE / TEE / StrongBox）
Android Keystore の鍵がどこで守られているかの段階です。 SOFTWARE は OS の中のソフトウェア実装、 TRUSTED_ENVIRONMENT は OS から隔離された実行環境（TEE）、 STRONGBOX は専用のチップです。 Keystore を使えば必ず TEE に入る、ということはありません。 いまどれなのかは KeyInfo の getSecurityLevel() で分かり、 アプリの「鍵がどこにあるか調べる」がその値を表示します。 エミュレータでは SOFTWARE と出るのが普通です。
getEncoded() が null であること
「この API から鍵のバイト列を取り出せない」という意味です。 ハードウェアで守られている証拠ではありません。 保護のレベルは上の getSecurityLevel() で別に確かめます。 2つは別の観測であって、片方からもう片方は導けません。

ここに判断の分かれ目がある

  • 鍵をコードに書くか、Keystore に生成させるか
  • 鍵を使うときに画面ロック解除を要求するか（setUserAuthenticationRequired）
  • 何から守るつもりなのか、落とした端末を拾った人か、root を取った攻撃者か

3つ目が一番大事で、そして一番よく飛ばされます。 落とした端末を拾った人と root を取った攻撃者とでは射程がまったく違うので、 同じ「暗号化しました」でも、どちらを想定したかで正解が変わります。章の終わりでここを判定します。

Basicアプリの中の鍵を取り出して、自分で復号する

所要 30分 / 初学者向け・必修。

1. アプリで暗号化する

第4章 → [Basic] 文字列を暗号化する を開き、適当な文字列を暗号化します。 出てきた Base64 の暗号文を控えておいてください。

2. APK から鍵を探す

まず APK が端末のどこにあるかを見ます。

adb shell pm path com.example.insecureappplatform
package:/data/app/~~xxxx==/com.example.insecureappplatform-yyyy==/base.apk

この長いパスは端末ごとに違うので、打ち写さず、そのまま取り出します。

adb pull "$(adb shell pm path com.example.insecureappplatform | sed 's/package://' | tr -d '\r')" base.apk
unzip -p base.apk 'classes*.dex' | strings | grep -iE "1234567890abcdef|AES/ECB"
1234567890abcdef
AES/ECB/PKCS5Padding

3. 手元で復号する

echo -n '<アプリが出した Base64>' | base64 -d | \
  openssl enc -d -aes-128-ecb -K 31323334353637383930616263646566
確認できたこと
アプリが「暗号化」した文字列を、アプリを使わずに読めてしまいました。 鍵が 1234567890abcdef という文字列のまま APK に入っている以上、 この暗号化は攻撃者に対して何の障壁にもなっていません。 APK は攻撃者の手元にあるファイルにすぎません。

いま立っていたのは APK だけ持っている人 です（攻撃者の立場）。端末にも通信路にも触れていないのに、鍵が手に入りました。

Basicで確認したこと
APKには固定鍵と復号に必要な情報が入っていたため、端末へ触れずに復号できました。 Standardでは暗号方式を増やさず、鍵の置き場所だけをKeystoreへ変えます。

Basic はここまで。 Standardでは同じ端末・同じアプリで鍵の置き場所だけを変え、 APK解析と端末上の観測結果がどう変わるかを確かめます。

Standard鍵をアプリの外に出す

所要 1〜2時間 / 中級者向け・推奨。

手を動かす順番
Basicで作ったbase.apkをそのまま使い、次の順で比較します。
  1. 被害者アプリで[Standard] 文字列を暗号化する (Keystore)を開き、文字列を入力して 「Keystoreの鍵で暗号化」を押す。
  2. 手順6のunzip | strings | grepを実行し、出力された文字列をそのまま控える。
  3. アプリへ戻り、「鍵がどこにあるか調べる」を押して、実装方式を確認する。
このStandardで判定するのは、鍵が見つかるか／鍵を使えるか／平文へ届くかの3つです。

5. Keystore 版で暗号化する

[Standard] 文字列を暗号化する (Keystore) を開いて暗号化します。 CryptoActivity との違いは鍵の置き場所だけであって、暗号アルゴリズムの話ではありません。

6. APK の中を同じ方法で探す

unzip -p base.apk 'classes*.dex' | strings | grep -i "tee_demo_key"

出てくるのは鍵の名前（alias）だけで、鍵そのものは入っていません。 鍵は生成された瞬間から Keystore の中にあり、アプリのコードにも変数にも現れません。

7. 鍵がどこにあるか調べる

アプリの 「鍵がどこにあるか調べる」 を押します。

alias = tee_demo_key (認証なしの鍵)
KeyInfo.getSecurityLevel() = SOFTWARE (ソフトウェア実装)
鍵の使用にユーザー認証が要るか: false
鍵の世代: 3f1a9c02

この値は端末の実測値であり、Android Keystore の鍵が常に
TEE や StrongBox にあるとは限らない。エミュレータでは SOFTWARE になる。
「Keystore を使った」は「TEE に入った」ではありません
エミュレータでは SOFTWARE と表示されることが多く、実機では TRUSTED_ENVIRONMENT（TEE）や STRONGBOX（専用チップ）になります。 Android Keystore を使ったからといって、鍵が必ずハードウェアで守られるわけではありません。

どの段でも「このアプリからは鍵の中身を取り出せない」点は同じです。 違うのは、OS のカーネルごと破られたときに耐えられるかどうかです。 だから「Keystore を使っているので鍵は TEE で保護されています」という診断文は、 この画面の実測値を添えない限り、根拠のない断定になります。 表示された値を見て、実装方式を勝手にTEEと決めつけないことが重要です。

Standard はここまで。 固定鍵はAPKから取得でき、Keystore版ではaliasしか見つからない、 という差を説明できれば十分です。「鍵を取り出せなくても使えるか」はAdvancedで確かめます。

# Keystore 画面を前面に出したまま、リポジトリのルートで実行する
frida -U -F -l tools/frida/ch4-use-keystore-key.js
[*] 鍵ハンドルを取得: android.security.keystore2.AndroidKeyStoreSecretKey
[*] 鍵の中身 getEncoded() = null  ← null なら取り出せていない
[*] 復号結果 = himitsu-no-memo
[*] 鍵は取り出せていないのに、平文は手に入った。
この章の山場
getEncoded() が null を返したことが、鍵を取り出せていない証拠です。 それでも himitsu-no-memo は手に入りました。 Android Keystore の認証なし鍵が直接守るのは鍵素材の非export性であり、 そのアプリに許された鍵の使用まで拒否するものではないからで、 使用の可否を決めているのは「そのアプリとして動けるか」、つまりプロセスの話であり、 第1章の話に戻ってきます。

11. 使用にも条件を付ける

先に：鍵は alias ごと分けてあります
.setUserAuthenticationRequired(true) にソースを書き換えて上書きインストールしても、 すでにある鍵の使用条件は変わりません。Keystore は alias で鍵を引くので、 同じ alias の鍵があればそれがそのまま返ってくるからです。 「1行変えたのに結果が変わらない」で止まるのはここです。

そこでこの教材では、条件の違う2本を別々の alias として持っています。 tee_demo_key（認証なし）と tee_demo_key_auth（認証つき）です。 暗号文も鍵ごとに別々に保存します。 鍵を作り直したら暗号文も作り直す必要があるからです。

アプリの Keystore 画面で 「認証つきの鍵 (tee_demo_key_auth)」 に切り替え、 その鍵で一度暗号化します。認証つきの鍵は暗号化にも認証が要るので、ここで一度認証を求められます。

エミュレータに画面ロック（PIN）か指紋が登録されていないと、 認証つきの鍵はそもそも作れません。 アプリが canAuthenticate の値を表示するので、その場合は設定から登録してください。

そのうえで 「認証せずに復号する」 を押します。

[未認証] UserNotAuthenticatedException
鍵は存在するが、ユーザー認証がまだなので Keystore が使用を断った。
判定しているのはアプリのコードではなく Keystore 側。

次に 「認証してから復号する」 を押します。 こちらは BiometricPrompt に CryptoObject を渡す正規の経路で、 認証の通った Cipher だけが返ってきます。今度は復号できます。

同じことを Frida からもやります。手順10 のスクリプトは2本の鍵を順に試すので、 認証なしの鍵は通り、認証つきの鍵は断られます。

何が変わったのか
Frida は相変わらずプロセスの中にいます。それでも失敗するのは、 鍵を使ってよいかを判定しているのがアプリのコードではなくKeystore の側だからです。 この端末・この鍵設定では、認証されていない暗号操作をKeystoreが拒否しました。
ただし「絶対に飛ばせない」ではありません
Keystore が強制しているのは鍵を使えるかどうかだけです。 利用者が自分で認証したあと、アプリが受け取る平文は、 相変わらず攻撃者と同じプロセスの中にあります。 認証を呼び出すアプリ側の処理も同じです。

つまりこの対策が動かしたのは「できる／できない」ではなく、 攻撃に必要な前提のほうです。 「プロセスに入れば復号できる」が「プロセスに入り、かつ利用者に認証させれば取れる」に変わりました。 攻撃面マップで ● が ◐ になる、というのがこれです。

11b. 失敗の種類を読み分ける

「この鍵を削除して作り直す」を押してから、暗号文はそのままで復号してみます。

[世代のずれ] 暗号文は鍵 3f1a9c02 で作られ、いまの鍵は b7e04d11。
この失敗は認証とは関係ない。

[復号失敗] AEADBadTagException
認証とは関係ない。鍵と暗号文の世代が合っていない。
これを「認証が効いた」と読まないこと
鍵を作り直すと、古い暗号文はもう復号できません。 これは認証による拒否ではありません。 実験中に鍵を作り直してしまうと、認証つきの鍵にしたから失敗したのか、 世代がずれたから失敗したのかが区別できなくなります。
失敗したときは、まず例外の種類を見てください。 UserNotAuthenticatedException なら認証、 AEADBadTagException なら世代のずれ、 KeyPermanentlyInvalidatedException なら画面ロック設定の変更です。

12. その先

  • StrongBox：TEE よりさらに独立した専用チップに鍵を置く
  • 鍵の attestation：「この鍵は本物のハードウェアで作られた」ことをサーバ側が検証する。 端末の自己申告ではなく、サーバが確かめる点が要点
  • Play Integrity：端末とアプリの状態をサーバが確認する

共通しているのは、判定をクライアントの外に出しているという一点です。 クライアント側の判定は、クライアントを支配した相手には効かないので、 第3章のピン留めと同じ結論に戻ってきます。

対策は効いたか。どこまで守るか

この章の冒頭で挙げた3つ目の分かれ目、何から守るつもりなのかに戻ります。 同じ「暗号化しました」でも、想定する相手が違えば判定が変わります。

攻撃者の能力ハードコード鍵Keystore の鍵Keystore + 認証要求
APK を手に入れた（静的解析）???
アプリのデータファイルだけを持っている???
ロック中の端末を物理的に取得した???
端末上で root を持ち、ファイルを読んでいる???
動作中のアプリのプロセスでコードを実行できる???

3行目と4行目を分けてあるのは、 「端末を奪われた」が1つの前提ではないからです。 ロック中の端末を拾っただけの相手は、まだどの列にも立てていません。

判定

Keystore が直接示したのは 鍵素材をこのAPIからexportできないことで、手順10では getEncoded() が null を返しました。 それでも、動いているアプリに「その鍵で復号して」と頼ませることはできてしまいます。 取り出せない ≠ 使えない。

だから setUserAuthenticationRequired が意味を持ちます。 鍵の使用に人間の操作を挟むと、プロセスを取っただけでは使えなくなるからで、 これは鍵をどこに置くかではなく、いつ使えるかを縛るという別の軸です。 ただし最後の行は ○ にはなりません。 利用者が認証したあとの平文は、攻撃者と同じプロセスの中にあるからです。 増えたのは「利用者に認証させる」という前提であって、到達不能になったわけではありません。

3行目（ロック中の端末を物理取得）は、どの列でも届きません。 ただしそれは暗号の効果というより、画面ロックが解けるまでユーザーデータが ファイルベース暗号化で保護されているという OS 側の仕組みによるものです。 「うちのアプリは端末を落としても安全です」と言うとき、 効いているのが自分の実装なのか OS なのかは区別してください。

まとめると、この章で確かめたのはこの一行です。 クライアント側の暗号は、端末の持ち主が敵になった場合を完全には守れません。 守れる範囲を正しく言えることが、守れると言い張るより重要です。

説明を書き終えてから開く：到達点の目安

  • Android Keystore は鍵の取り出しを防ぎますが、鍵の使用は防ぎません
  • getEncoded() が null であることと、ハードウェアで守られていることは別の話です
  • 使用を制限したければ、条件をアプリの外（Keystore 側）に置く必要があります。 ただしそれで守れるのは鍵の使用だけで、認証後の平文はプロセスの中に残ります
  • クライアント側だけで完結する防御には限界があり、最終的にはサーバ側の検証が要ります
