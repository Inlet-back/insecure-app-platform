第1章とのつながり
第1章で「他アプリからは読めない」ことを確かめた user_session の中身が、 この章では他アプリから普通に読めてしまいます。ファイルの権限は何ひとつ変わっていません。 変わったのは、アプリが自分で窓口を開けたことだけです。
初めての人の最短ルート
Basic手順2で公開Providerを読む → StandardのP3・P4・P4bだけを比べる → 章末で exported=false とsignature permissionを判定してください。 ActivityとReceiverは同じ境界の発展例です。

この章で触る仕組み

読むだけ・7分。第1章で見た「箱」に、今度は窓口を開ける話です。

アプリは他のアプリと連携して動きます。写真を選び、共有ボタンで別のアプリに渡す。 そのために Android が用意しているのがこの章の仕組みで、 窓口を開けるのは普通の使い方です。決めるのは誰に開けるかのほうです。

仕組みを詳しく読む（図・問答・用語）

Q1. アプリ同士は互いのメモリを触れません。ではなぜ、共有ボタンで写真を別のアプリに渡せるのですか。

渡しているのではなく、Binder というカーネルのドライバ越しに頼んでいるからです。

頼み方の型が2つあります。相手のデータを取りに行く窓口が ContentProvider で、 連絡先やカレンダーを読めるのもこれです。Manifest の <provider> に書いた authorities が名前になり、content://<authority>/<path> という URI で呼ばれます。

もう1つが Intent で、「これをしてくれ」というメッセージを投げる形です。 受け口が BroadcastReceiver、宛先が <intent-filter> に書いた action 名になります。 Binder の実体は /dev/binder というデバイスファイルです。

Q2. 窓口を開けたとして、誰が来ますか。

指定しなければ、その端末に入っている全員です。

それを決める1行が android:exported で、 Activity にも Provider にも Receiver にも、同じ書き方で付きます。

ここで押さえておきたいのは、この1行が APK の中の Manifest に書いてあることです。 攻撃者も同じものを読めます。窓口の名前を推測しにくいものに変えても、隠したことにはなりません。

Q3. 開けたまま、相手を選べますか。

選べます。permission で「この資格を持つ相手だけ」と要求します。

守る側が <permission> で名前と protectionLevel を宣言し、 呼ぶ側が <uses-permission> で要求する、という形です。

強さが2段階あります。normal は呼ぶ側が自分の Manifest に1行書けば取れてしまいますが、 signature は宣言した側と同じ証明書で署名されたアプリにしか与えられません。 この差がこの章の分かれ目になります。

この教材の攻撃者アプリは、その1行を実際に書いています。 書いたうえで付与されないことを P4b で確かめられます。 「宣言していないから弾かれた」のと「宣言したが署名が違うので付与されなかった」のは別で、 後者でなければ signature が効いた証拠になりません。 2つのモジュールは別々の鍵で署名してあり、 tools/verify/verify-signatures.sh がそれを自動で確かめます。

もう1つ、Intent には送り主を証明する情報が自動では付きません。 誰から来たのかを確かめるかどうかは、受け取る側が決めることになります。

この章で触る4つは、中のコードではなく Manifest の書き方だけが違います。 第1章で見たファイルの権限は、4つとも同じままです。

窓口Manifest の書き方外から呼ぶとプローブ
SessionProviderexported=true / permission なし 中身が出てくるP3
AdminActivityexported=true ログイン画面を通らずに開くP5
RoleReceiverexported=true / intent-filter あり 送り主を確かめずに信じるP7
ProtectedSessionProviderpermission あり（signature） 手前で弾かれるP4

一番上と一番下は、中身のコードが同じクラスです。 違うのは Manifest の1行だけで、結果が逆になります。

判定しているのは誰か：アプリのコードではなく ActivityManager / ContentResolver（システム側）です。 見ているのは Manifest の exported と permission で、 呼び出しがプロセスを跨ぐ前に弾かれます。

用語だけをもう一度並べる（問答で出たものの一覧。あとで引く用）
IPC（プロセス間通信）と Binder
アプリは別々のプロセスで動くので、相手のメモリを直接は触れません。 やり取りは Binder というカーネルのドライバを経由します。
ContentProvider
他アプリに自分のデータを渡す窓口で、連絡先やカレンダーを読めるのもこれです。 Manifest の <provider> に書いた authorities が名前になり、 content://<authority>/<path> の URI で呼ばれます。
Intent と BroadcastReceiver
Intent は「これをしてくれ」というメッセージ、Receiver はその受け口です。 Manifest の <intent-filter> に書いた action 名が宛先です。 届いた Intent に、送り主を証明する情報は自動では付きません。
android:exported
他アプリから呼べるかどうかの指定です。 Activity / Provider / Receiver のどれにも、同じ1行で付きます。
permission と protectionLevel
呼ぶ側に資格を要求する仕組みです。守る側が <permission> で名前と protectionLevel（normal か signature）を宣言し、 呼ぶ側は <uses-permission> で要求します。

ここに判断の分かれ目がある

窓口を1つ作るたびに、作り手は毎回この4つを決めています。

  • exported を true にするか false にするか
  • permission を付けるか、付けないか
  • 付けるならどの protectionLevel か（normal / signature）
  • 受け取った Intent の中身を信じるか、送り主を確かめるか

この4つの組み合わせが、そのまま攻撃の成否になります。 この章では コードを一切変えずに Manifest の 1行だけ を動かして、結果がどう変わるかを見ていきます。

Basic窓口から入ってみる

所要 30分 / 初学者向け・必修。

1. 画面を名指しで開く

このアプリには [Basic] 管理者コンソール という画面があります。 アプリのメニューから開くのが本来の入り方ですが、端末の外から名指しで起動できます。

adb shell am start -n com.example.insecureappplatform/.AdminActivity

管理者コンソールが開きます。アプリの画面をひとつも通っていません。 誰が呼んだのかは確認されず、呼ばれたとおりに開きました。

2. 窓口からデータを持ち出す

第1章で保存した認証情報を、アプリの画面を使わずに取り出します。

adb shell content query --uri content://com.example.insecureappplatform.session/creds
Row: 0 key=username, value=alice
Row: 1 key=password, value=P@ssw0rd123

出てくる行は user_session に保存されている内容そのものです。 第1章をまだやっていなければ空になります。

確認できたこと
第1章では Permission denied で止められた同じ P@ssw0rd123 が、 ContentProvider 経由なら、authorityを知り窓口を呼べる別アプリやshellから読めてしまいます。ファイルの権限は変えていません。 アプリが自分で外に向けた口を開けただけです。

adb shell content query は、公開窓口の挙動を観測する教材用プローブです。 本章で判定する攻撃者は、脅威ブリーフに置いた別UID・別署名の通常アプリであり、StandardのP3/P4で同じ結果を確かめます。

Basicのゴール：ファイル権限を迂回した経路を説明する
次へ進む前に、結果を次の3点に分けてください。
  1. 外から直接開けたコンポーネントは何でしたか。
  2. 第1章では読めなかったデータを、今回はどの窓口から読みましたか。
  3. この結果だけで、通常の別アプリからも読めると判定できますか。
答え合わせ

AdminActivityと、公開されたSessionProviderが外から到達できました。 ファイルを直接読んだのではなく、Providerに被害者アプリ自身の権限で読ませています。 ただし今回はshellを観測用に使ったため、通常アプリでも成立することはStandardのP3で確かめます。

Basic はここまで。 Standardでは、同じ操作をAttackerアプリから試します。 「誰でも使える入口」と「入場券を持つアプリだけが使える入口」で、結果がどう変わるかを比べます。

Standard何が窓口を開け、何が閉めているのか

所要 1〜2時間 / 中級者向け・推奨。

最初は、Attackerアプリの3つのボタンだけ試します
この章ではアプリを2つ使います。 InsecureAppPlatformが調べられる側、Attackerが外からアクセスを試す側です。 P3などの名前はAttackerアプリに表示されるボタン番号なので、暗記する必要はありません。 Providerは、あるアプリが別のアプリへデータを渡すためのデータの窓口です。
  1. 準備：InsecureAppPlatformを開き、第1章の [Basic] ログイン情報を保存するでユーザー名とパスワードを保存します。 すでに保存してあれば、やり直さなくて構いません。
  2. 公開設定を比べる：手順3のコマンドを実行し、Androidが拒否する画面を確認します。
  3. 3つのボタンを押す：Attackerアプリを開き、 P3「無防備なProviderを読む」→ P4「permissionで守ったProviderを読む」→ P4b「permissionが付いたか調べる」の順に押します。
  4. ボタンの下に出る結果を読む：1つ押すたびに下半分のログを読み、 その場の設問で結果を選びます。3つをまとめて押さないでください。
  5. コードで答え合わせ：3つの結果を記録したあと、手順5のコマンドを実行します。 2つのprovider設定を並べ、異なる行を自分で探します。
最後に手順5でManifestを開き、結果を変えた1行を確認します。

3. もう1つの画面を外から開いてみる

adb shell am start -n com.example.insecureappplatform/.InsecureStorageActivity
Permission Denial: starting Intent { cmp=com.example.insecureappplatform/.InsecureStorageActivity }
from ... (pid=5428, uid=2000) not exported from uid 10175
これは OS が止めた
同じ am start、同じアプリなのに、片方は開いて片方は止まります。 違いは AndroidManifest.xml の android:exported の値だけです。 止めた側も not exported from uid 10175 と、誰のものかを見て弾いたことを言っています。 判定しているのはアプリのコードではなく、ActivityManager（システム側）です。

4. 本編：Providerを攻撃者アプリから比較する

まずAttackerアプリのP3を押し、ボタンの下に出るログを確認します。

次にP4を押します。P3と同じデータを読む操作ですが、こちらの窓口には入場券が必要です。 P4の結果を見たあと、P4bで入場券が実際に付与されたか確認します。

5. Manifest 側で答え合わせをする

grep -A3 "provider" \
  app/src/main/AndroidManifest.xml

P3 と P4 の Provider は 中身のクラスが同じ（ProtectedSessionProvider は SessionProvider をそのまま継承しているだけです）。違いは Manifest の1行だけです。

<provider android:name=".SessionProvider"
    android:authorities="...session"
    android:exported="true" />

<provider android:name=".ProtectedSessionProvider"
    android:authorities="...session.protected"
    android:exported="true"
    android:permission="com.example.insecureappplatform.permission.READ_SESSION" />
攻撃を止めたのはコードではない
P4 が止まったのは Java/Kotlin のコードのおかげではなく、 Manifest に書いた1行と、それを見て ContentResolver がプロセスをまたぐ前に チェックしているおかげです。防御はアプリの中ではなく、境界の上にあります。

6. 直す

  • SessionProvider を exported="false" にする（そもそも公開しない）
  • 公開が必要なら signature permission を付ける

Standard はここまで。P3とP4の結果を変えたのがManifestの1行であり、 判定したのはAndroid側だと説明できれば十分です。

Advanced窓口の下を覗く（任意）

任意。

8. 公開されている入口を全部数える

adb shell dumpsys package com.example.insecureappplatform | grep -B2 -A6 "Activity Resolver"

実機のアプリを調べるときは、まずここで「外から触れる面」を数えるところから始まります。 面が多いほど、攻撃対象は広くなります。

9. アプリ同士の会話はどこを通っているのか

adb shell ls -l /dev/binder
crw-rw-rw- 1 root root 10, 50 2026-09-04 14:20 /dev/binder

Intent も ContentProvider も、最終的にはこのカーネルのドライバを通ってプロセス間を渡っています。 権限チェックが「アプリの中」ではなく「境界の上」にあると言えるのは、 実際に別プロセス・別特権のコード（system_server）が間に立っているからです。

この先（本プラットフォームの拡張余地）
Binder はカーネルドライバなので、その実装自体が攻撃対象になり得ます。 アプリ層の脆弱性からカーネル層の脆弱性へ話が続くのはこの地点です。本章では扱いません。

対策は効いたか。どこまで守るか

この章の窓口に対しては、次のような修正案がよく出てきます。 どれが本当に効くのかを判定するのは、あなたです。 攻撃側（P3〜P7）は一切変えずに、Manifest だけを動かして確かめてください。

出てきた修正案効くか効かないなら、なぜ
Provider の URI を推測しにくい名前に変える??
exported="true" のまま permission (normal) を付ける??
exported="true" + permission (signature)??
exported="false" にする??
Receiver 側で intent.getStringExtra の値を検証する??
Receiver 側で Binder.getCallingUid() を見て送信元を確認する??
判定

1つ目は効きません。URI は APK の Manifest に書いてあり、攻撃者はそれを読めます。 隠すことは守ることではありません。

2つ目も効きません。normal は攻撃側が自分の Manifest に 1行書けば取れてしまいます。止まったように見えて、止まっていません。 「permission を付けました」という報告を受け取ったら、まず protectionLevel を聞いてください。

3つ目と4つ目は効きます。ただし射程が違います。signature は 「同じ署名鍵の自社アプリからは使わせる」、exported="false" は 「誰にも使わせない」という線の引き方です。連携が必要かどうかで、正解が変わります。

5つ目は的を外しています。値が正しいかではなく そもそも誰でも投げられる点が問題です。 role に admin 以外を弾いても、攻撃者は admin を送ってきます。 値の検証は、到達を絞ったあとの二重化としては意味がありますが、単独では防御になりません。

6つ目はいちばん危ない誤答です。ブロードキャストの受信処理では、 Binder.getCallingUid() は送信元の UID を返さないため、送信元の確認には使えません（Standard 手順7 の囲みを参照）。 「送信元を確認している」ように見えるコードが書けてしまい、実際には誰でも通ります。 止めるのは exported か receiver の permission の側です。

AI に「この Provider を直して」と聞くと、1つ目や2つ目が返ってくることがあります。 実験でそれを棄却できるようになるのが、この章の到達点です。

章末：手を動かした結果を言葉にする

最後に、今回の観測から言えることを短く整理します。

説明を書く

説明を書き終えてから開く：到達点の目安
  • プロセス境界が守られていても、アプリが窓口を開ければデータは出ていく
  • exported と permission を判定しているのはアプリではなくシステム側
  • protectionLevel が normal か signature かで、同じ「permission あり」でも結論が変わる
  • Intent は外部入力であり、中身をそのまま権限や認証状態として信用できない
  • ブロードキャストでは送信元の UID を受信側で確かめられない。止めるのは exported と permission の側
