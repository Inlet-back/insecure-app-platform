この章で触る仕組み

読むだけ・7分。第1章で見た「箱」に、今度は窓口を開ける話です。

アプリは他のアプリと連携して動きます。写真を選び、共有ボタンで別のアプリに渡す。 そのために Android が用意しているのがこの章の仕組みで、 窓口を開けるのは普通の使い方です。決めるのは誰に開けるかのほうです。

仕組みを詳しく読む（図・問答・用語）

Q1. アプリ同士は互いのメモリを触れません。ではなぜ、共有ボタンで写真を別のアプリに渡せるのですか。

渡しているのではなく、Binder というカーネルのドライバ越しに頼んでいるからです。

頼み方の型が2つあります。相手のデータを取りに行く窓口が ContentProvider で、 連絡先やカレンダーを読めるのもこれです。Manifest の <provider> に書いた authorities が名前になり、content://<authority>/<path> という URI で呼ばれます。

もう1つが Intent で、「これをしてくれ」というメッセージを投げる形です。 受け口が BroadcastReceiver、宛先が <intent-filter> に書いた action 名になります。 Binder の実体は /dev/binder というデバイスファイルです。

Q2. 窓口を開けたとして、誰が来ますか。

指定しなければ、その端末に入っている全員です。

それを決める1行が android:exported で、 Activity にも Provider にも Receiver にも、同じ書き方で付きます。

ここで押さえておきたいのは、この1行が APK の中の Manifest に書いてあることです。 攻撃者も同じものを読めます。窓口の名前を推測しにくいものに変えても、隠したことにはなりません。

Q3. 開けたまま、相手を選べますか。

選べます。permission で「この資格を持つ相手だけ」と要求します。

守る側が <permission> で名前と protectionLevel を宣言し、 呼ぶ側が <uses-permission> で要求する、という形です。

強さが2段階あります。normal は呼ぶ側が自分の Manifest に1行書けば取れてしまいますが、 signature は宣言した側と同じ証明書で署名されたアプリにしか与えられません。 この差がこの章の分かれ目になります。

この教材の攻撃者アプリは、その1行を実際に書いています。 書いたうえで付与されないことを P4b で確かめられます。 「宣言していないから弾かれた」のと「宣言したが署名が違うので付与されなかった」のは別で、 後者でなければ signature が効いた証拠になりません。 2つのモジュールは別々の鍵で署名してあり、 tools/verify/verify-signatures.sh がそれを自動で確かめます。

もう1つ、Intent には送り主を証明する情報が自動では付きません。 誰から来たのかを確かめるかどうかは、受け取る側が決めることになります。

この章で触る4つは、中のコードではなく Manifest の書き方だけが違います。 第1章で見たファイルの権限は、4つとも同じままです。

窓口Manifest の書き方外から呼ぶとプローブ
SessionProviderexported=true / permission なし 中身が出てくるP3
AdminActivityexported=true ログイン画面を通らずに開くP5
RoleReceiverexported=true / intent-filter あり 送り主を確かめずに信じるP7

一番上と一番下は、中身のコードが同じクラスです。 違うのは Manifest の1行だけで、結果が逆になります。

判定しているのは誰か：アプリのコードではなく ActivityManager / ContentResolver（システム側）です。 見ているのは Manifest の exported と permission で、 呼び出しがプロセスを跨ぐ前に弾かれます。

用語だけをもう一度並べる（問答で出たものの一覧。あとで引く用）
IPC（プロセス間通信）と Binder
アプリは別々のプロセスで動くので、相手のメモリを直接は触れません。 やり取りは Binder というカーネルのドライバを経由します。
ContentProvider
他アプリに自分のデータを渡す窓口で、連絡先やカレンダーを読めるのもこれです。 Manifest の <provider> に書いた authorities が名前になり、 content://<authority>/<path> の URI で呼ばれます。
Intent と BroadcastReceiver
Intent は「これをしてくれ」というメッセージ、Receiver はその受け口です。 Manifest の <intent-filter> に書いた action 名が宛先です。 届いた Intent に、送り主を証明する情報は自動では付きません。
android:exported
他アプリから呼べるかどうかの指定です。 Activity / Provider / Receiver のどれにも、同じ1行で付きます。
permission と protectionLevel
呼ぶ側に資格を要求する仕組みです。守る側が <permission> で名前と protectionLevel（normal か signature）を宣言し、 呼ぶ側は <uses-permission> で要求します。

ここに判断の分かれ目がある

窓口を1つ作るたびに、作り手は毎回この4つを決めています。

  • exported を true にするか false にするか
  • permission を付けるか、付けないか
  • 付けるならどの protectionLevel か（normal / signature）
  • 受け取った Intent の中身を信じるか、送り主を確かめるか

この4つの組み合わせが、そのまま攻撃の成否になります。 この章では コードを一切変えずに Manifest の 1行だけ を動かして、結果がどう変わるかを見ていきます。

2. 窓口からデータを持ち出す

第1章では、別のアプリから user_session の保存ファイルを 直接は読めないことを確かめました。ファイルの持ち主が違うからです。

Standard何が窓口を開け、何が閉めているのか

所要 1〜2時間 / 中級者向け・推奨。

この節で使うもの
この章ではアプリを2つ使います。 InsecureAppPlatformが調べられる側、Attackerが外からアクセスを試す側です。 P3などの名前はAttackerアプリのボタンに書いてある参照番号なので、暗記する必要はありません。 Providerは、あるアプリが別のアプリへデータを渡すためのデータの窓口です。
  1. 準備：InsecureAppPlatformを開き、第1章の [Basic] ログイン情報を保存するでユーザー名とパスワードを保存します。 すでに保存してあれば、やり直さなくて構いません。
  2. 手順3：この章で触る窓口の宣言を、先に Manifest で読みます。
  3. 手順4：非公開の画面を am start で開きます（ターミナル）。
  4. 手順5：2つの Provider を Attacker から読みます（Attackerアプリ）。
手順3で読んだ数行が、手順4と手順5で「到達できるか」を決めます。

手順4と手順5は、どの操作も「予測を記録してから1回だけ実行する」順で進めてください。 予測を入れるまで、その手順の結果例と解説は開きません。

3. まず Manifest を読む

ここから先は、操作の前に結果を予測して記録します。予測には根拠が要ります。 根拠は1つのファイルにまとまっています。この章で触る窓口は、 AndroidManifest.xml に全部宣言されているからです。先に開いてください。

まず画面（Activity）を数えます。

grep -A2 "<activity" app/src/main/AndroidManifest.xml \
  | grep -oE 'android:(name|exported)="[^"]*"'
android:name=".MainActivity"
android:exported="true"
android:name=".InsecureStorageActivity"
android:exported="false"
...
android:name=".AuthActivity"
android:exported="false"
android:name=".AdminActivity"
android:exported="true"
...

画面は9つありますが、exported="true" は2つだけです。 1つはランチャーアイコンから起動される MainActivity、 もう1つが Basic 手順1で外から開いた AdminActivity です。 第2章のもう1枚の画面 AuthActivity（ログイン画面）は false になっています。

次に、データの窓口（Provider）を並べます。

grep -A4 "<provider" app/src/main/AndroidManifest.xml
<provider
    android:name=".SessionProvider"
    android:authorities="com.example.insecureappplatform.session"
    android:exported="true" />
--
<provider
    android:name=".ProtectedSessionProvider"
    android:authorities="com.example.insecureappplatform.session.protected"
    android:exported="true"
    android:permission="com.example.insecureappplatform.permission.READ_SESSION" />

どちらも exported="true" で、違うのは android:permission の1行があるかないかだけです。 中身のクラスも同じで、ProtectedSessionProvider は SessionProvider をそのまま継承しているだけです。

Manifest で分かるのは「誰が呼べるか」までです
呼んだ結果どんなデータが返るかは、ここには書いてありません。 authorities は窓口の名前であって、中身の目録ではないからです。 返る中身は実装側にあり、それが Basic 手順2で読んだ SessionProvider の4行でした。

このあとの手順4と手順5で予測するのは、到達できるかどうかのほうです。 予測の理由欄には「Manifest のどの行を見たか」を書いてください。

この Manifest はビルド後の APK にも入っています。 ソースを持たない相手でも、APK を展開すれば同じものを読めます。 端末側から数える方法は Advanced 手順8 にあります。 窓口の名前を推測しにくくしても、隠したことにはなりません。

4. 同じ章の非公開の画面を外から開いてみる

Basic 手順1で開いた管理者コンソールは exported="true" でした。 第2章にはもう1枚、"false" の画面があります。ログイン画面 (AuthActivity) です。 同じコマンドで、そちらを開きます。

adb shell am start -n com.example.insecureappplatform/.AuthActivity
補足：Attackerから画面を開く操作との違いは？（P5・P6）

この手順ではターミナルを使います。AttackerのP5・P6も画面の起動を要求しますが、 呼び出す側はshellではなく、別UIDの通常アプリになります。

  1. Attackerが起動したい画面の名前を指定したIntentを作ります。
  2. startActivity() でAndroidに起動を要求します。
  3. 呼び出しが戻ったか、例外が出たかを表示します。実際の画面表示は対象アプリ側で確認します。

P5は管理者画面、P6は非公開の画面との比較用です。 起動要求が例外なしで戻ったことと、画面上の操作が成功したことは別です。 この手順では資料に書かれたターミナル操作を行い、P5・P6の追加実行は必須ではありません。

Starting: Intent { cmp=com.example.insecureappplatform/.AuthActivity }

Exception occurred while executing 'start':
java.lang.SecurityException: Permission Denial: starting Intent { ... } from null
(pid=10642, uid=2000) not exported from uid 10185
これは OS が止めた
同じ am start、同じアプリの同じ章の画面なのに、片方は開いて片方は止まります。 違いは手順3で読んだ android:exported の値だけです。 止めた側も not exported from uid ... と、誰のものかを見て弾いたことを言っています。 末尾の数字は被害者アプリの UID で、端末やインストールのたびに変わります。 判定しているのはアプリのコードではなく、ActivityManager（システム側）です。
ここで言えるのは「到達できる」までです
管理者コンソールが開いたことは、認証を突破したことではありません。 この教材のログイン画面は Login Success と表示するだけで、 管理者コンソールへ遷移しません。2つの画面はコードの上ではつながっていないので、 越えるべき関門がそもそも実装されていません。

確かめたのは「exported な画面には外から到達できる」ことだけです。 実際のアプリで同じことが起きたとき、そこから先に何ができるかは、 その画面が何を表示し何を実行するかを見て別に判定します。 到達と実行は分けて数えてください。

5. 本編：Providerを攻撃者アプリから比較する

ここからは Attacker アプリで操作します。手順4 までと違い、 adb ではなく、権限を何も持たない普通のサードパーティアプリが呼び出す側になります。 操作は2つ。どちらも予測を記録してから、1回だけ実行してください。

操作1：無防備な窓口を読む。 Basic 手順2で content query から読んだのと同じ SessionProvider を、今度は別アプリから呼びます。 Attacker アプリの P3 がこの操作です。

補足：Attackerは何をしている？（P3）

処理の流れ：Attacker → Providerへの問い合わせ → 対象アプリが返すデータ → Attackerの表示。

  1. AttackerがProviderの宛先URIを指定し、ContentResolver.query() を呼びます。
  2. 呼び出しが許可されると、対象アプリの SessionProvider が 自分の user_session を読み、結果を返します。
  3. Attackerが返された行を読み、項目名と値を表示します。

第1章のP1ではAttackerがファイルを直接開こうとしました。 P3ではデータを持つアプリ自身に読ませます。 同じデータでも、誰がファイルを読むかが変わっています。

見るところ：返された件数と内容です。0件なら、呼び出しから空の結果が返っています。 アクセス拒否とは区別し、対象アプリでテストデータを保存済みか確認してください。

操作2：permission を付けた窓口を読む。 ProtectedSessionProvider を呼びます。読みにいくデータは操作1 と同じで、 クラスの中身も同じです。Attacker アプリの P4 がこの操作です。

補足：P4とP4bは、それぞれ何を調べる？

P4はデータの問い合わせです。P3と同じAPIを使い、 permission付きの ProtectedSessionProvider を宛先にします。 Attackerは返されたデータ、または呼び出し時の例外を表示します。

P4bは権限と署名の照会です。データを読む操作とは別に、次の3点をAndroidの情報から調べます。

  • AttackerのManifestにpermissionの要求が書かれているか。
  • そのpermissionが実際にAttackerへ付与されているか。
  • Attackerと対象アプリの署名が一致するか。

使う順序：予測を記録してP4を実行し、結果を確認したあとにP4bを使います。 permissionを要求したことと、付与されたことを分けて読んでください。 P4bは状態を調べるだけで、permissionを付与する操作ではありません。

攻撃を止めたのはコードではない
P4 が止まったのは Java/Kotlin のコードのおかげではなく、 手順3で読んだ android:permission の1行と、それを見て ContentResolver がプロセスをまたぐ前に チェックしているおかげです。防御はアプリの中ではなく、境界の上にあります。

6. 直す

  • SessionProvider を exported="false" にする（そもそも公開しない）
  • 公開が必要なら signature permission を付ける

Standard はここまで。P3とP4の結果を変えたのがManifestの1行であり、 判定したのはAndroid側だと説明できれば十分です。

9. アプリ同士の会話はどこを通っているのか

adb shell ls -l /dev/binder
crw-rw-rw- 1 root root 10, 50 2026-09-04 14:20 /dev/binder

Intent も ContentProvider も、最終的にはこのカーネルのドライバを通ってプロセス間を渡っています。 権限チェックが「アプリの中」ではなく「境界の上」にあると言えるのは、 実際に別プロセス・別特権のコード（system_server）が間に立っているからです。

この先（本プラットフォームの拡張余地）
Binder はカーネルドライバなので、その実装自体が攻撃対象になり得ます。 アプリ層の脆弱性からカーネル層の脆弱性へ話が続くのはこの地点です。本章では扱いません。

対策は効いたか。どこまで守るか

補足：設定変更のボタンは何をしている？（P7・P7b／任意）

Providerがデータを問い合わせる窓口なのに対し、この教材のReceiverは設定変更のメッセージを受け取る窓口です。 本編のP3・P4を終えるために、P7・P7bを追加実行する必要はありません。

  1. Attackerが対象アプリ宛てのIntentに変更内容を入れます。
  2. sendBroadcast() でAndroidへ送信を依頼します。
  3. 送信処理が戻ったことを表示します。対象Receiverから受信・変更完了の通知が返る仕組みではありません。

P7bはpermission付きの窓口との比較用です。 ログの「送信できた」と、対象の設定が変わったことを区別してください。 設定変更の結果を見る場所は対象アプリの管理画面です。 状態が変わらなかった場合も、それだけでは配送されなかったとは断定できません。

この章の窓口に対しては、次のような修正案がよく出てきます。 どれが本当に効くのかを判定するのは、あなたです。 攻撃側（P3〜P7）は一切変えずに、Manifest だけを動かして確かめてください。

出てきた修正案効くか効かないなら、なぜ
Provider の URI を推測しにくい名前に変える??
exported="true" のまま permission (normal) を付ける??
exported="true" + permission (signature)??
exported="false" にする??
Receiver 側で intent.getStringExtra の値を検証する??
Receiver 側で Binder.getCallingUid() を見て送信元を確認する??
判定

1つ目は効きません。URI は APK の Manifest に書いてあり、攻撃者はそれを読めます。 隠すことは守ることではありません。

2つ目も効きません。normal は攻撃側が自分の Manifest に 1行書けば取れてしまいます。止まったように見えて、止まっていません。 「permission を付けました」という報告を受け取ったら、まず protectionLevel を聞いてください。

3つ目と4つ目は効きます。ただし射程が違います。signature は 「同じ署名鍵の自社アプリからは使わせる」、exported="false" は 「誰にも使わせない」という線の引き方です。連携が必要かどうかで、正解が変わります。

5つ目は的を外しています。値が正しいかではなく そもそも誰でも投げられる点が問題です。 role に admin 以外を弾いても、攻撃者は admin を送ってきます。 値の検証は、到達を絞ったあとの二重化としては意味がありますが、単独では防御になりません。

6つ目はいちばん危ない誤答です。ブロードキャストの受信処理では、 Binder.getCallingUid() は送信元の UID を返さないため、送信元の確認には使えません。 「送信元を確認している」ように見えるコードが書けてしまい、実際には誰でも通ります。 止めるのは exported か receiver の permission の側です。

AI に「この Provider を直して」と聞くと、1つ目や2つ目が返ってくることがあります。 実験でそれを棄却できるようになるのが、この章の到達点です。

説明を書く

説明を書き終えてから開く：到達点の目安
  • プロセス境界が守られていても、アプリが窓口を開ければデータは出ていく
  • exported と permission を判定しているのはアプリではなくシステム側
  • protectionLevel が normal か signature かで、同じ「permission あり」でも結論が変わる
  • Intent は外部入力であり、中身をそのまま権限や認証状態として信用できない
  • ブロードキャストでは送信元の UID を受信側で確かめられない。止めるのは exported と permission の側
