この章で触る仕組み

読むだけ・7分。端末の外には、OS の隔離は届きません。

アプリがサーバと通信するのは、ごく普通のことです。通信を TLS で包み、 相手の証明書を端末が持つ信頼の一覧と突き合わせ、その方針をアプリが設定ファイルで宣言する、 というのが普段の守り方です。 この章で見るのは、その普通の通信で何がどこに置かれ、誰が判断しているのかのほうです。

仕組みを詳しく読む（図・問答・用語）

Q1. HTTPS は何を守っていますか。2つあります。

盗み見されないこと（暗号）と、相手が誰か（証明書の検証）です。

後者が崩れると、前者も意味を失います。 偽物と正しく暗号化して話したところで、守られたことにはならないからです。 この章で何度も戻ってくるのは、2つ目のほうです。

Q2.「相手が誰か」は、何を根拠に判断していますか。

証明書をたどった先の trust anchor を、端末が信じているかどうかです。

サーバの証明書は認証局（CA）が署名しています。 サーバ証明書 ← 中間 CA ← ルート CA という証明書チェーンをたどり、 行き着いた起点の CA が trust anchor です。

端末が信じている CA の一覧がトラストストアで、2種類あります。 システム証明書は OS に同梱・管理されるもので、通常の利用者が任意に追加することはできません。 ユーザー証明書は利用者が設定画面から後で足せるもので、 Android 7 以降、アプリは既定ではこちらを信じません。

Q3. その「信じる／信じない」を決めているのは誰ですか。

アプリのほうです。検証を実行するのは OS ですが、何を信じるかはアプリが宣言します。

宣言の置き場所が Network Security Config（実体は app/src/main/res/xml/network_security_config.xml）で、 宛先ごとに平文を許すか、どの trust anchor を使うかを、コードではなく宣言で書きます。

もう1つ、通常の検証に上乗せして、相手の公開鍵のハッシュまで照合する 公開鍵ピン留めがあります。この教材では実体をアプリのコード （NetworkActivity.pinningSocketFactory()）に置いていますが、 ピンニングを採用する場合は、手書きTrustManagerより NSC の <pin-set> で宣言するほうが 検証順序を誤りにくくなります。ただしAndroid公式は、一般的なアプリへのピンニング自体を推奨していません。
置き換えではなく上乗せというのが要点で、 通常の検証（チェーン・有効期限・発行者）を飛ばしてピンだけを見る実装にすると、 期限切れの証明書でも「ピンさえ合えば通る」実装になります。この話はAdvancedで扱います。

第1章と第2章では、判定していたのは全部 OS でした。 この章からアプリの書き方が結果を変えます。 差分実験でコードを1行も変えずに結果がひっくり返るのは、そのためです。

「HTTPS だから安全」の中身は、次の4段です。 このうちどこが緩んでいるかで、経路上の第三者に中身が渡るかどうかが決まります。 ③と④を決めているのがアプリ側だ、というのがこの章の出発点です。

段決めているのは実体
① サーバが証明書を出すサーバサーバ証明書 ← 中間 CA ← ルート CA
② その CA を端末が信じているかOS システム証明書ストア（追加には root が要る）／ユーザー証明書ストア
③ どちらのストアを使うかアプリ res/xml/network_security_config.xml
④ ③に加えて公開鍵まで照合するかアプリ NSC の <pin-set>（推奨）／ NetworkActivity.expectedPin（教材の手書き実装）

Android 7 以降、アプリは既定ではユーザー証明書ストアを信じません。 Burp の CA を端末に入れても HTTPS が読めないのは、この既定が効いているからです。

守っているのは誰か：OS の検証処理と、アプリ自身の宣言の両方です。 証明書を検証するのは OS ですが、何を信頼するかを決めるのは NSC とアプリのコードです。 第1〜2章と違い、ここはアプリ側の書き方が結果を大きく変えます。

用語だけをもう一度並べる（問答で出たものの一覧。あとで引く用）
HTTPS が守っているもの
2つあります。盗み見されないこと（暗号）と、相手が誰か（証明書の検証）です。 後者が崩れると前者も意味を失います。
証明書チェーンと trust anchor
サーバの証明書は認証局（CA）が署名しています。 その CA を端末が信じているかどうかで、検証の可否が決まります。 この起点になる CA を trust anchor と呼びます。
トラストストア（システム証明書とユーザー証明書）
端末が信じている CA の一覧で、2種類あります。システム証明書は OS に同梱されているもので、 ここに足すには root が要ります。ユーザー証明書は利用者が端末の設定画面から 後で足せるもので、Android 7 以降、アプリは既定ではこちらを信じません。
Network Security Config (NSC)
実体は app/src/main/res/xml/network_security_config.xml で、 AndroidManifest.xml の android:networkSecurityConfig から結び付けています。 宛先ごとに平文を許すか（cleartextTrafficPermitted）、どの trust anchor を使うかを、 コードではなく宣言で決める仕組みです。
公開鍵ピン留め
通常の証明書検証を通したうえで、さらに相手の公開鍵のハッシュまで一致を要求するやり方です。 通常の検証の置き換えではありません。 置き場所は NSC の <pin-set>（宣言）か、 アプリのコード（この教材の NetworkActivity）です。 鍵を更新するとピンも変わるので、予備のピンを併記し、 expiration を切って「アプリを更新できないまま全員が接続不能になる」事故を避けます。 Android の公式ドキュメントは、一般のアプリにピンニングを推奨していません。 運用の失敗で自分のアプリだけが落ちるリスクのほうが大きいことが多いからです。

ここに判断の分かれ目がある

  • 平文（HTTP）で送るか、TLS で包むか
  • ユーザー証明書を信じるか（デバッグのために許した設定が、そのまま出荷されることがあります）
  • 公開鍵をピン留めするか（守れる相手は増えますが、鍵の更新や期限切れでアプリが接続できなくなる運用リスクを引き受けます）

この章の差分実験は、アプリのコードを一切変えずに CA をどこに置くかと NSC の 1行だけを動かします。結果が変わるなら、 それは「暗号の強さ」の話ではなかったわけです。

StandardHTTPS は何を守っているのか

所要 1〜2時間 / 中級者向け・推奨。

手を動かす順番
ターミナル、アプリ、Burpを同時に見るので、先に役割を固定します。
  1. ターミナルAでpython3 tools/mockserver/server.pyを起動したままにする。
  2. アプリで「2. HTTPSで送る」を押し、接続結果とエラー表示を記録する。
  3. Burpを使える場合は手順5を行い、HTTP historyに本文が出る条件だけを比較する。
必修は手順4までです。Burpを準備できる場合だけ手順5を追加します。

4. HTTPS で送る

アプリで「2. HTTPS で送る」を押します。押す前に、下で結果を予測してください。

[失敗] SSLHandshakeException
Trust anchor for certification path not found.
これは通信が壊れたのではない
暗号が失敗したわけでも、サーバが落ちているわけでもありません。 「この相手を信じてよい」と判断できなかったという意味です。 モックサーバの証明書は教材用の CA が発行したもので、その CA が端末の信頼ストアに載っていません。 証明書自体は正しく作られていて、期限も切れていません。 足りないのは「発行者を端末が知っているか」だけです。
TLS が守っているのは「盗み見」だけではなく、「相手が誰か」でもあります。

5. 差分実験：CA をどこに入れるかで結果が変わる

Burp Suite（または手順の証明書）の CA 証明書を端末に入れて、毎回「2. HTTPS で送る」を押します。 アプリのコードは一切変えません。

Burpを使う場合の具体的な操作
  1. BurpのProxy listenerをホスト側の8081で起動します（モックサーバの8080とは分けます）。
  2. adb shell settings put global http_proxy 10.0.2.2:8081で、エミュレータの通信をBurpへ向けます。
  3. BurpのCAをエミュレータへユーザーCAとして入れます。この時点で「2. HTTPSで送る」を押し、まだ拒否されることを確認します。
  4. network_security_config.xmlの<certificates src="user" />を有効にし、 ./gradlew :app:installDebugで入れ直して、同じボタンを押します。
  5. BurpのHTTP historyでPOST /loginを選び、Request本文の username=...&password=...を確認します。

実験後はadb shell settings put global http_proxy :0でプロキシ設定を解除し、 NSCのコメントも元に戻してください。

続けて比較する場合だけ、network_security_config.xmlの <certificates src="user" />を有効にして再インストールし、同じ操作を繰り返します。

<trust-anchors>
    <certificates src="system" />
    <certificates src="user" />   <!-- ← これを有効にする -->
</trust-anchors>
./gradlew :app:installDebug
ここが第3章の核心
Burp で HTTPS が読めなかったのは、暗号が強かったからではありません。 アプリがその CA を信頼していなかったからです。 Android 7 (API 24) 以降、アプリは既定でユーザー追加の CA を信頼しません。 つまり「HTTPS だから安全」ではなく、信頼ストアに何が載っているかで安全性が決まります。 「HTTPS なので問題ありません」と書かれた診断結果を見たら、 まず信頼ストアの話に置き換えて読み直してください。

Standard はここまで。 HTTPSの成否は「暗号化したか」だけでなく、 アプリがどのCAを信頼したかで変わる、と説明できれば十分です。

6. ピン留めは外せる

ピン照合をしているのはアプリのコードです。ということは、 アプリのプロセスに入り込める相手にはその判定を書き換えられます。 checkServerTrusted を何もしない関数に差し替えれば、ピン留めは無効になります。

第1章 手順11 と同じ構造
鍵を Keystore に置いても、プロセスに入られたら鍵は使われます。
ピンをコードに書いても、プロセスに入られたら判定は飛ばされます。
クライアント側の防御は、クライアントを支配した相手には効きません。 これは第4章の主題そのものです。

7. では何のためにピン留めするのか

「破れるなら意味がない」ではありません。想定する攻撃者が違います。

「守れる／守れない」ではなく「誰から守れるか」で書けるようになること。

対策は効いたか。どこまで守るか

「HTTP をやめて HTTPS にしました」で終わらせません。 何から守れて、何から守れないのかを判定します。 HTTPS にした時点で満足してしまうと、ピン留めが何のためにあるのか分からないまま終わります。

攻撃者の位置HTTPHTTPS（既定）HTTPS + ピン留め
通信を観測・中継できるon-path攻撃者???
端末にユーザー証明書を入れられる???
端末が root 化されている???
アプリのプロセスに Frida を入れられる???
判定

HTTPS が守るのは 経路上の他人 までです。 端末の持ち主が敵になった瞬間、trust anchor は持ち主が足せます。 「HTTPS だから安全」は、攻撃者が経路上にいる場合に限った話です。

ピン留めは一段強いのですが、これもアプリの中の判定なので、 プロセスを取られれば書き換えられます（Deep）。 通信の防御は、端末そのものを敵に渡した時点で全部やり直しになります。

逆に言えば、ピン留めが守るのは「利用者が騙されて偽の CA を入れてしまった」場合です。 誰を想定するかで、入れるべきかどうかが変わります。

説明を書き終えてから開く：到達点の目安
  • 端末内で OS が守っていたデータも、経路に出れば別の話になります
  • HTTPS が守るのは盗み見だけでなく「相手が誰か」でもあります
  • Burp で読めるかどうかは、暗号の強さではなく信頼ストアの中身で決まります
  • ピン留めは通常の TLS 検証の上乗せであって、置き換えではありません
  • ピン留めはアプリ自身の防御であり、プロセスを取られると無効になります
  • ピン留めには鍵更新・期限切れという運用リスクがあり、Android は一般のアプリには推奨していません
