導入 — モバイルのセキュリティは何でできているか

読むだけ・15分。手を動かす前の座学はこの1ページだけです

座学のみ 15分
このページのゴール
モバイルのセキュリティが何でできているかを押さえ、 これから4章で何を確かめに行くのかと自分がどの立場で確かめるのかを 先に決めておくためのページです。 あわせて、この先ずっと使う問いの立て方を3つ渡します。

1. 3つの問いから始めます

モバイルのセキュリティが何でできているのかを、3つの問いと答えで見ます。

Q1. モバイルアプリには、「入れたら即マルウェア感染」というイメージがありません。なぜですか。

理由はあります。ただし、アプリを信用してよいという話とは違います。 PC と比べたときに、OS がアプリに渡している権限の単位が違うのです。

PC では、あなたがログインして起動したソフトは、あなたの権限をそのまま受け取ります。 ユーザーはあなた1人ぶんしかないので、長く使っている表計算ソフトも、 さっき拾ってきたばかりのツールも、同じ「あなた」として同じ書類に手が届きます。

Android は、アプリを1つインストールするたびに Linux のユーザーを1人作ります。 第1章で ls -l を打つと u0_a175 という名前で出てきます。 アプリ同士は、同じ端末の中で動いている別々のユーザーです。

つまり、あまり警戒せずに入れられているのは、アプリが信用できるからではなく、 OS が最初から信用しない前提で置き場所を分けているからです。

Q2. それは仮想メモリによる隔離のことですか。そして、他のアプリのデータが読めないとき、止めているのは誰ですか。

仮想メモリの隔離とは別の話です。プロセスごとにメモリ空間を分ける仕組みは PC にも昔からあります。

違うのは、ファイルと IPC とプロセス操作について、権限を誰の単位で数えるかです。 PC は「ユーザー」単位なので、同じユーザーが起動したソフトは同じ UID を持ち、互いのファイルを直接開けます。 Android は「アプリ」単位なので、他のアプリの持ち物は所有者が一致せず、カーネルに弾かれます。 どうしても読みたければ、持ち主のアプリに IPC で仲介してもらうしかありません。

止めているのはアプリのコードではなく、カーネルです。 ファイルを開こうとした時点で、持ち主の UID と rw-rw---- のような並びが照合されます。 守られている側のアプリは「守ってください」と頼んですらいないので、 なぜ守られているのかの答えは、アプリのソースをどれだけ読んでも書いていません。

ついでに範囲を押さえておきます。Unix でいう「ファイル」は書類だけを指しません。 /dev のデバイスも /proc の中身も同じ枠組みで扱われるので、 カメラやマイクに触れるかどうかも、この照合の上に乗っています。

Q3. では、モバイルは安全なのですか。

安全になったのではなく、攻撃の行き先が移っただけです。

塞がったのは、他のアプリが勝手にファイルを直接開く経路です。 ここは本当に塞がっていて、第1章では読めることと読めないことの両方を自分の手で確かめます。

代わりに、隔離があるからこそ生まれた攻撃があります。 Q2 で出てきた仲介の窓口の作り方を誤って外から入られる、 あるいは権限を持っている側に代わりに仕事をさせる、といった形です。 端末の外に出る通信は、誰でも通れる場所を通ります。そして、土台ごと壊しにくる人もいます。

ここで1つ押さえておきます。カメラを扱う cameraserver のようなプロセスは、 カーネルとは別の層にいます。専用のユーザーと SELinux のラベルを与えられた、 ユーザー空間の特権プロセスです。この手の仕組み自体は PC にもあって、 Linux の polkit、Windows のサービス、macOS のデーモンがそれにあたります。

ここが差の出るところです。 違うのは仕組みの有無ではなく強制力のほうです。 PC では、特権プロセスを迂回して一般のソフトがデバイスを直接開けてしまうことがよくあります。 Android は SELinux で迂回路そのものを塞いでいます。 隔離が「守っている」と言えるのは、迂回できないところまで含めて見たときです。

迂回できないので、攻撃者の労力はより下の層に集中します。 移った先の4つが、そのままこの教材の4つの章です。

2. いま出てきたものを、図と名前で押さえる

3つの答えに出てきた「箱」には実体があります。

UID（Linux ユーザー ID）
Android はアプリを1つインストールするたびに、Linux のユーザーを1人作ります。 つまりアプリ A とアプリ B は、同じ端末の中で動いている別々のユーザーであって、 ファイルの持ち主も、読み書きできるかどうかも、すべてこの ID で決まります。
専用のデータ領域
/data/data/<パッケージ名>/ がそのアプリの箱の中身です。 インストール時に OS が作り、そのアプリの UID の持ち物にします。
DAC（持ち主とパーミッションの照合）
開こうとしたファイルの持ち主と、rw-rw---- のような並びを照合します。 第1章では ls -l を打って、この並びを実際に見ます。
SELinux
Linux のユーザー分離の上にもう一層載っている、カーネル側の仕組みです。 「この種類のプロセスは、この種類のファイルにしか触れない」を強制しています。 第1章で ls -Z を打つと、その存在だけは見えます。
プロセスの隔離
アプリはそれぞれ別のプロセスとして動きます。 他のアプリのメモリを覗くことは、普通の方法ではできません。 ただしこれは PC にも昔からある仕組みです。 Android で変わったのは、DAC が何を単位に照合するかのほうです。

3. どの経路でデータに届くかを、4章で比べる

この教材の4章は、脆弱性の種類ではなくどの境界が破れたかで分けてあります。

章箱の話でいうと実体
第1章 プロセス境界 箱の中の置き方が雑だと、箱が開いたときに困る UID 分離、/data/data の権限、SELinux
第2章 IPC 境界 箱には窓口がある。作り方を間違えると外から入られる Binder、Intent、exported、permission
第3章 ネットワーク境界 箱の外に出る通信は、誰でも通れる場所を通る TLS の信頼モデル、トラストストア、NSC
第4章 Android Keystoreと鍵の使用 箱そのものを壊す人がいる。そこでも守れるのか Android Keystore、鍵の保持と使用の分離

この順番には理由があります。 第1章で「箱がある」ことを確かめ、第2章と第3章で「箱に開いている口」を見て、 最後の第4章では箱が壊された状態を前提にするので、 4つの別々の技を覚えるのではなく、ひとつの話の続きとして読めるはずです。

ここからは、この教材の進め方です

4. この教材でのあなたの立場

出てきた主張が本当かを確かめる人として進みます。

脆弱性を見つけられること自体の価値は、以前より下がりました。 自動解析ツールと AI が、それなりの精度で候補を並べてくれるからです。 ただし AI が出してくるのは、あくまで主張であって事実ではありません。

  • 「ここが脆弱です」→ 本当に成立するのか
  • 「こう直せば安全です」→ その修正は本当に効くのか
  • 「暗号化したので安全です」→ 何から安全になったのか
あなたは検証者
攻撃するのは確かめるためであって、破ること自体が目的ではありません。 対策を書くのでもなく、出てきた対策が効くかどうかを判定します。

これは AI に質問するときの構えでもあります。 各章には AI に聞くための文が置いてあり、返ってきた説明はその章の手順でそのまま検証できます。 章末では自分の言葉で説明を書きます。 合っているかどうかを決めるのは、AI ではなく手元のエミュレータです。

5. どの立場から攻めるのか

脆弱性より先に、誰として攻めるのかを決めます。

4章は「どの境界が破れるか」で並んでいます。ただし章を開いた時点で、 どこが破れるかも、使う道具も、成功するかどうかも、こちらが決めてしまっています。 実際の診断では順番が逆になり、先に決めるのは相手のほうです。 Android の設計を書いた The Android Platform Security Model という文書も、 機構の説明より先に、どういう相手をどこまで想定するのかを並べています。

想定する相手が決まっていないと、あとで「この対策は効いていますか」と聞かれたときに答えようがありません。 効くかどうかは、相手によって変わるからです。 ひとつ前の節で決めたのは検証者として進むという構えでした。ここで決めるのは、確かめるときに誰の役をやるかです。

肩書ではなく、能力で切ります
「端末を奪った人」は1つの立場ではありません。 ロック中の端末を拾っただけの人、ロックが解けた端末を触れる人、root を取った人、 バックアップのファイルだけを持っている人では、できることがまるで違います。 カードは肩書ではなく、その相手が実際に持っている能力で切ってあります。

新しく用意した道具は1つもありません。各章の Basic ですでに使うものに、名前と前提を付けただけです。 カードは3行で固定してあります。3行目のそこに立つには何が要るかを毎回読んでください。 攻撃が現実的かどうかは、だいたいこの行で決まります。

APK だけ持っている 端末の外

unzip / apktool / grep

できること
コードと Manifest と同梱リソースを全部読めます。窓口の名前も、直書きした鍵もここで出ます。
できないこと
動いている端末の中の値には、1つも届きません。
立つには
配布されている APK を手に入れるだけです。端末には触りません。

通信路にいる人 端末の外

Burp（同じ Wi-Fi・中間者）

できること
端末の外に出ていくパケットを覗けます。条件が揃えば書き換えもできます。
できないこと
端末の中に置いてあるだけのものには届きません。
立つには
同じ Wi-Fi に入る、経路上の機器を押さえる。端末の中には入っていません。

開発者の口 端末の中

adb shell / run-as / content query

できること
shell ユーザーとして端末を操作できます。run-as でアプリのデータにも入れます。
できないこと
run-as が効くのは debuggable なアプリだけです。ストアのリリース版では通りません。
立つには
ユーザーが開発者オプションと USB デバッグを自分で有効にしている必要があります。
いま読むのはこの3枚だけです
立場は全部で7つあり、残り4枚は取得済みファイル・攻撃者アプリ・root・Frida を使う層のものです。 そちらは 攻撃面マップ の側に置いてあります。 章を通したあと、1つの資産にどの立場から届くのかを数えるときに、7枚まとめて使います。

6. 各章は必ず2つをセットで見る

防御側があることが、この教材と一般的な「やられアプリ」との違いです。

攻撃側防御側
どうやって漏れるか なぜ普段は漏れないのか（OS が裏で何をしているか）

ps、ls -l、id といった素の道具を使って、 守っている当人である OS の仕事を、自分の目で見に行きます。

先に言っておきます：失敗する演習があります
わざと成功しない手順が入っていて、そこには「これは OS が守った結果です」と必ず書いてあります。 コマンドが弾かれたとき、それはあなたの操作ミスではなく観察対象です。

7. 1つの章の進み方

全4章が同じ6段でできています。

どの章でも迷わないように、形は固定してあります。

段やること
① この章で触る仕組み読む。何を相手にするのかを押さえる（5分）
② 判断の分かれ目作り手がどこで選んでいるかを見る。まだ答えは出ない
③ 間違った判断の結果予測してから攻撃する
④ なぜ普段は破れないのかOS の側に回って観察する
⑤ 修正案が効くかを判定する効く案と、効いたように見える案を見分ける
⑥ その対策はどこまで守るか守れない範囲を「失敗」ではなく射程の外として言う

時間がなければ ①③⑤ だけでも章は閉じます（Basic）。 層の分け方は トップページにあります。

③と④では、打つ前に予測を書きます
コマンドを打って結果を眺めるだけだと、「そういうものか」で終わります。 先に予測を書くと、外れた瞬間に自分の思い込みが表に出ます。そこが学習の起点です。 予測を書かせるだけでは飛ばされるので、この教材では 予測を入れるまで解説が出ません。手順ごとに欄が埋め込んであり、操作はページの中で完結します。
外してよい
的中率は高ければよいものではありません。外した手順は 記録 に残り、 どこで誤解していたかの記録になります。むしろそこが成果物です。

⑥まで終わったら、章末に 説明課題 があります。 4〜5問に自分の言葉で答えて、必要な観点が入っているかを自己採点します。 抜けている観点には、どの手順に戻ればよいかが出ます。 そのあとが 概念テスト と オラクル演習 で、 前者には実際によくある誤解が選択肢として仕込んであり、後者は AI が出した診断と修正案を判定する課題です。

8. 最初の3問が、この先で使う質問の型です

答えの中身と同じくらい、問いの立て方を持ち帰ってほしいと思っています。

3問はそれぞれ違う型で立ててあり、この教材はこの3つを4章ぶん繰り返します。

型導入での例この先どこで使うか
比較で立てる Q1: PC と何が違うのか ③。条件を1つだけ変えて、結果の差だけを見る
守る側を主語にする Q2: 誰が止めているのか ④。攻撃する側ではなく、止める側に立つ
どの脅威に対してかを問う Q3: 何に対して安全とされるのか ⑥。守れる範囲と守れない範囲に線を引く

「安全ですか」と聞くと答えが出ません。「何から守りますか」と聞くと答えが出ます。 この差が、各章の最後で修正案を判定するときにそのまま効いてきます。

9. 手を動かす前にひとつだけ約束

実施範囲
すべてローカルの AVD（または自分で用意した検証端末）の上で、 自分がインストールしたアプリに対してのみ実施してください。 外部のサービスやアプリには接続しません。
