第1章 — プロセス境界

アプリは箱に入っている。その箱を誰が閉めているのかを見る

MASVS-STORAGE-1 Basic 30分 Standard 1〜2時間 Deep 任意
この章のゴール
「平文で保存すると危ない」と知っているだけでは足りません。 普段はなぜ他のアプリから読めないのか、 どの条件が崩れると読めてしまうのか、 暗号化はどこまで守ってどこから守らないのか を、自分の手で確かめて言えるようになることです。

この章で触る仕組み

読むだけ・7分。手を動かす前に、何を相手にするのかだけ押さえておきます。

アプリが自分のデータを端末に保存するのは、ごく普通のことです。 ログイン状態、設定、下書き、どれも毎回サーバに聞きに行くわけにはいきません。 この章で見るのは、その普通の保存がどこに置かれて、そこに誰が手を伸ばせるのかのほうです。

Q1. アプリがログイン状態を覚えているとき、それはどこに書かれていますか。

SharedPreferences です。キーと値を XML に書くだけの、ごく普通の API です。

実体は /data/data/<パッケージ名>/shared_prefs/<名前>.xml にあります。 この /data/data/<パッケージ名>/ 全体がアプリのデータ領域で、 インストールのときに OS が作り、そのアプリ専用にします。 この章で読みに行く user_session.xml も、ここに入っています。

Q2. その領域は、他のアプリから見ると誰の持ち物ですか。

そのアプリ専用の UID、つまり専用の Linux ユーザーの持ち物です。

Android はアプリを1つインストールするたびに、Linux のユーザーを1人作ります。 ls -l を打つと u0_a175 のような名前で出てくるのがそれで、 ファイルの持ち主はこの UID です。

並びは rw-rw---- です。先頭を除いた9文字を3つずつ区切ると、 順に持ち主・グループ・その他全員に何ができるかを表していて、 rw- は読み書き可、--- は何もできません。 最後の3桁が --- なので、持ち主とそのグループ以外は読むことも書くこともできません。 アプリ同士は、OS から見れば赤の他人のアカウントです。

Q3. では、これから打つコマンドで、なぜ中身が読めるのですか。

run-as を挟んで、そのアプリの UID になりすますからです。

adb shell は端末の中でコマンドを打つための入口ですが、 shell という別のユーザーとして動きます。 Q2 の並びに当てはめると「その他全員」にあたるので、そのままでは読めません。 run-as は debuggable なアプリに限って、その壁を越えさせる開発用の仕組みです。

つまり手順2 の成功は、このアプリの守りが甘いからではなく、 開発用の抜け道を1つ使っているからです。 ここを知らないまま打つと run-as はただの呪文になり、 手順4 でなぜ失敗するのかも分からなくなります。

止まる場所は、どの立場から手を伸ばしたかで変わります。 この章で打つコマンドの結果は、全部この表のどれかになります。

手を伸ばす側誰として動いているか結果手順
攻撃者アプリ（別 UID）自分の UID。被害者とは別人 開けない手順6
adb shell（そのまま）shell ユーザー。これも別人 開けない（Permission denied）手順4

結果は「誰として手を伸ばしたか」で決まります。 返ってくるエラーの文言は端末によって変わりますが、 結論を決めているのはエラーコードではなく、この「誰として」のほうです。 そこは手順6 でもう一度確かめます。

守っているのは誰か：アプリのコードではなく OS です。 Linux のファイル所有権とパーミッションが、アプリ同士を隔てています。 アプリ側は「守ってください」と頼んですらいません。

用語だけをもう一度並べる（問答で出たものの一覧。あとで引く用）
SharedPreferences
アプリごとの小さな設定置き場。キーと値を XML で保存します。実体は /data/data/<パッケージ名>/shared_prefs/<名前>.xml。 ログイン状態や設定を持たせるのによく使われる、普通の API です。
アプリのデータ領域
/data/data/<パッケージ名>/。インストール時に OS が作り、そのアプリ専用にします。
UID（Linux ユーザー ID）
Android は 1つのアプリに 1つの Linux ユーザーを割り当てます（u0_a175 のような名前）。 ファイルの持ち主はこの UID で、パーミッションもこれで決まります。
パーミッション（rw-rw---- の読み方）
先頭を除いた9文字を3つずつ区切り、順に持ち主・グループ・その他全員に何ができるかを表します。 rw- は読み書き可、--- は何もできません。 つまり rw-rw---- は「持ち主とそのグループだけが読み書きでき、他は一切触れない」という意味です。 手順5 でこの並びを実際に見ます。
adb shell と run-as
adb shell は端末の中でコマンドを打つための入口で、shell という 別のユーザーとして動きます。run-as は debuggable なアプリに限り、 そのアプリの UID になりすませる開発用の仕組みです。

ここに判断の分かれ目がある

ログイン状態を端末に持たせるとき、作り手は必ずこのどれかを選んでいます。

  • 平文のまま端末に置く
  • 暗号化して端末に置く（では鍵はどこに置く？）
  • そもそも端末に置かない（毎回サーバに聞く）

この章で検証するアプリは 1つ目を選んでいます。 どの選択がどこまで守るのかは、手を動かしたあとで判定します。

5. 誰が持ち主なのかを見る

アプリごとに別のユーザー ID が割り当てられていることを確認します。

adb shell pm list packages -U | grep -E "insecureappplatform|attacker"
package:com.example.attacker uid:10177
package:com.example.insecureappplatform uid:10175

ファイルの持ち主も見ておきます。

adb shell run-as com.example.insecureappplatform ls -l shared_prefs/
-rw-rw---- 1 u0_a175 u0_a175 162 2026-09-04 14:30 user_session.xml
Android の一番大事な設計
1アプリ = 1人の Linux ユーザー。u0_a175 がこのアプリの正体です。 パーミッションは rw-rw----。最後の3桁が --- なので、持ち主とそのグループ以外には読み権限がありません。 アプリ同士は、同じ端末に住んでいても OS から見れば赤の他人のアカウントです。 だから手順4 は止まりました。

エラーの文言は、結論の根拠にしない
P1 のエラーをよく読んでください。手順4 の adb shell では Permission denied（EACCES）でしたが、攻撃者アプリからだと ENOENT (No such file or directory) と出ることがあります。 ファイルは確かに存在するのに「無い」と言われます。

ここで「ENOENT だからこういう仕組みだ」と決めないでください。 何が返るかは、パス・Android のバージョン・SELinux と DAC のどちらで先に落ちたか・ Java の API 経由か native の open() かで変わります。 Android 11 以降はアプリごとに別のマウント名前空間が与えられる構成もあり、 その場合は権限判定の手前で見えなくなります。

結論はエラーコードではなく、仕組みのほうに置きます。 別 UID のアプリから被害者の private data に届かないのは、 UID の分離・ファイル権限（DAC）・SELinux が重なって効いているからです。 エラーの文言はこの端末で観測した症状であって、隔離の理由そのものではありません。 報告書に書くなら、どの端末のどのバージョンで何が返ったかまで添えてください。

ヒント：この表から何を読み取るか

「暗号化したから安全」ではなく、攻撃者に何ができるかで結論が変わることを読み取ってください。 暗号化が効くのは、オフラインで取り出したファイルしか持っていない相手です。 バックアップを手に入れただけ、吸い出したデータを渡されただけ、という立場がこれにあたります。

一方、動いている端末で root を持っている相手には効きません。 下から2行目と最後の行は、同じ root です。違うのは、ファイルを読んで諦めたか、 そこからプロセスに入ったかだけです。 「root には効きません」と「root でファイルを読んでも中身は出ません」は両立します。 前者が最終的な到達可能性、後者がその1経路の話だからです。 報告書に書くときは、どちらを言っているのかを明示してください。

Standard はここまでです。 「アプリの実装ミス」と「OS の保護」が二階建てになっていることを説明できれば到達です。

9. ユーザー分離の上にもう一枚ある

adb shell run-as com.example.insecureappplatform ls -Z shared_prefs/
u:object_r:app_data_file:s0:c175,c256,c512,c768 user_session.xml

これは SELinux のラベルです。UID による権限（DAC）とは別に、 カーネルが「どのラベルのプロセスが、どのラベルのファイルに触れてよいか」を強制しています（MAC）。 UID を偶然一致させられても、こちらが残ります。

10. root で読む

adb root
adb shell cat /data/data/com.example.insecureappplatform/shared_prefs/user_session_secure.xml

暗号化されたままで、読めません。ファイルを読み出す経路に対しては、暗号化がちゃんと効いています。 ただし、ここで止まるかどうかは攻撃者が決めることです。手順11 へ進みます。

つまり 保存時の暗号化は root 対策になりません。 守っているのは「端末やファイルだけを奪われた場合」であって、 「アプリのプロセスに入り込める相手」ではありません。

ヒント：B と C の違いはどこにあるか

ECB はブロックごとに独立して暗号化するので、平文の繰り返しが暗号文にそのまま出ます。 CBC は前のブロックと連鎖するのでそれは消えますが、先頭の IV が毎回同じなら 同じ平文からは毎回同じ暗号文が出ます。C が直したのは一部だけです。

判定

暗号化が効くのは「ファイルを持ち出された」場合までです。 アプリのプロセスそのものを取られたら効きません。 鍵は Keystore にあって取り出せませんが、動いているアプリに 「その鍵で復号して」と頼ませることはできるからです（Deep 手順11）。

言い換えると、保存時の暗号化は root 対策ではなく、落とした端末を拾われた場合の対策です。 「暗号化したので安全です」という主張は、どちらを想定しているかを言わない限り判定できません。

  • その上に SELinux による強制アクセス制御がもう一枚あります
