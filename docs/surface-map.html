攻撃面マップ

章を終えたあとに戻ってくる、1枚の表を埋める演習

このページのゴール
章は「どの境界が破れるか」で並んでいます。ここでは並べ方を変えて、 1つの資産に何通りの経路があるのかを数えます。 使う語彙は 攻撃者の立場 の7枚のカードです。
この表が何を数えているか
列は「攻撃者の肩書」ではなく能力・アクセス経路です。 数えるのは、その能力から最終的にその資産へ到達できるかどうかで、直接できることだけではありません。
● 直接届く / ◐ 前提をもう一段足せば届く / ○ 届かない / — 対象外。
◐ を ○ と書かないでください。root の列を ○ にしてしまうと、 root からプロセス内実行へ進める経路が表から消えます。 根拠の欄に 未検証 と付いているマスは、 この教材で実際には確かめていないものです。 届かないことと、確かめていないことは別ものです。

章は境界で切ってあります。これは守る側の地図です。 守る側は経路を1本ずつ塞ぐので、「ファイルの権限」「窓口」「通信」と分かれているほうが仕事に合っています。

攻める側の入り口は資産です。認証情報が1つあるとして、それが端末のどこに現れるかを数えると、 保存されたファイル、窓口の向こう側、通信の途中、鍵で包まれた状態と、いくつも出てきます。 章ぶんの内容を、1つの資産の話として並べ直すと表になります。

どこから始めるか
表は3枚あり、自分が通した層のものだけをやります。 Basic だけを通した人は最初の1枚で終わりです。先の2枚は、まだ打っていない手順を含みます。 思い出せないことと、確かめていないことは別ものです。迷ったら章へ戻って打ち直してください。

Basic4つの資産に、3つの立場から

4行・20分。各章の Basic で実際に打った結果だけで埋まります

ここに出てくる3つの立場は、すでに全部使っています。 第1章の run-as と第2章の content query が開発者の口、 第3章の Burp が通信路、第4章で APK を grep したのが「APK だけ」です。

1行ずつ、届く立場を全部選んでください。選んで確定するまで答えは出ません。

初学者はここまでで終わりです。 4つの資産が、それぞれ違う立場から狙われることが分かれば、この演習の目的は果たしています。

表に出てくる立場（残りの4枚）

Basic の表で使った3枚は 導入 にあります。 ここから先の表では列が増え、次の4枚が加わります。カードは3行で固定してあり、 3行目のそこに立つには何が要るかで、その列がどのくらい現実的かが決まります。

同じ端末の普通のアプリ 端末の中

attacker アプリ（P0〜P7b）

できること
公開されている窓口を叩けます。自分の UID で通る操作なら全部できます。
できないこと
他アプリのファイルを直接開けません。別 UID なので所有者が一致しません。
立つには
ユーザーにアプリを1つ入れてもらうだけです。特別な権限は要りません。

アプリのデータファイルだけを手に入れた 端末の外

バックアップの展開 / 吸い出したデータ / adb pull の結果

できること
その時点のファイルの中身を、時間をかけて調べられます。端末は手元になくて構いません。
できないこと
端末の上で何かを実行できません。Keystore に鍵を使わせることも、窓口を叩くこともできません。
立つには
バックアップを手に入れる、吸い出されたデータを受け取る。端末そのものには触れていません。

動いている端末で root を持っている 端末の中

adb root / ファイル直読み / デバッガ / Frida の設置

できること
UID の照合を無視してファイルを読めます。さらに、動いているプロセスを覗き、止め、 コードを注入できます。この最後の1つが、1枚下のカードへの入口です。
できないこと
ファイルが読めることと、中身が読めることは別です。 Android Keystore が管理している鍵のバイト列は、それでも直接は取り出せません。 どこまで耐えるかは端末の保護レベル次第で、 アプリの「鍵がどこにあるか調べる」に出る実測値で決まります。
立つには
root 化済みの端末を使う、ブートローダを開ける、OS の脆弱性を使う。 ロックの解けた端末が手元にあることが前提です。

動いているアプリの中 端末の中

Frida

できること
アプリ自身として振る舞えます。アプリにできることは全部できます。
できないこと
アプリにできないことはできません。権限はアプリのものを超えません。
立つには
この教材では root を取ったエミュレータに frida-server を置きます。 root端末のカードから上がる段として扱っているのは、そのためです。
教材の前提と、技術一般の制約は別です
この教材が root を要求しているのは、手順を1本に固定するためであって、 Frida 一般が root を必要とするからではありません。 非 root の端末でも、次のような経路でプロセス内にコードを持ち込めます。
  • Frida Gadget を組み込んで APK を再パッケージし、自分の鍵で署名し直す
  • android:debuggable="true" のアプリにデバッガとして接続する
どちらも「アプリを配布された形のまま動かす」前提を崩しますが、 root は取っていません。root → Frida が唯一の経路ではありません。 この先の表で root の列を評価するときは、 「root がなければプロセス内に入れない」とは読まないでください。

「端末を奪った」は、これ1枚では表せません

物理的に端末を手に入れただけでは、アプリのデータには届きません。 間に立ちはだかるものが違うので、少なくとも次の4つは別の前提として扱います。

前提そこから何ができるかこの表のどの列か
ロック中の端末を物理的に取得した ほぼ何もできません。画面ロックが解けるまで、ユーザーデータは ファイルベース暗号化で保護されたままです どの列にも立てていません
ロックが解けた端末を操作できる 画面から見えるものは見えます。開発者オプションが有効なら adb shell の列に上がれます adb shell（条件付き）
root / OS を侵害した ファイルを直接読め、プロセスにも入れます。 ただしブートローダのアンロックはデータ消去を伴う構成が多く、 「端末を拾ったからここに立てる」わけではありません root端末（→ プロセス内）
バックアップやファイルのコピーだけを持っている ファイルの中身は調べられますが、端末の上では何も実行できません 取得済みファイル

第1章の暗号化が効くのはいちばん下の行に対してで、 上から3行目に対しては効きません。「端末を奪われても安全です」という一文は、 この4つのどれを指しているのかを言わないと判定できません。

強い順に一直線には並びません

導入の3枚とここまでの3枚は、上から下へ強くなっていくように読めます。端末の中に限ればそのとおりで、 普通のアプリより adb shell が広く、その上に root があります。ここは段になっています。

一方で、通信路にいる人は端末の中のファイルに一切届きませんし、 root を取った人も、経路を流れる暗号文をそのまま読めるわけではありません。 強さが一直線なら、表は階段状になるはずです。そうならないことを、この先の3枚で確かめます。

Standard列が3本増える

7行・40分。攻撃者アプリ（P1〜P7b）と root を使った人向け

立場に取得済みファイル・別アプリ・root端末 が加わり、 資産に「暗号化したあとの中身」「permission で守った窓口の先」「HTTPS で送信中」が加わります。

「取得済みファイル」と「root端末」を分けているのが要点です。 バックアップを1つ手に入れただけの相手と、動いている端末で root を持っている相手は、 できることが違います。第1章の暗号化は前者には効きますが、後者には効きません。 1つの列にまとめてしまうと、この差が言えなくなります。

さっきと同じ行がもう一度出てきます。 列が増えた状態で、もう一度考えてください。答えは前の表とは別に記録されるので、 前に何を選んだかは気にしなくて構いません。

Standard はここまで。 ここまでで、防御が効いている範囲を列の数で言えるようになっています。

Deep最後の1列

10行・任意。Frida でプロセスの中に入った人向け

最後にプロセス内の列が増え、資産に Keystore の鍵、鍵の使用、 そして認証つきの鍵の使用が加わります。

注目してほしいのは、新しく増えた2行より、前の表にもあった行のほうです。 列が1本増えただけで結論がひっくり返る行があります。どれがそうなるかを、選ぶ前に考えてみてください。

表が埋まったら

持ち帰ってほしいのは3つです。

1つ目。防御とは、この表のマスが ● から ◐ や ○ へ動くことです。 第1章で暗号化を入れたとき、消えたのは「取得済みファイル」と adb shell の列でした。 root の列は消えず、● から ◐ に変わっただけです。そこからプロセス内実行へ進めるからです。 第3章で HTTPS にしたとき、消えたのは経路上の1列だけで、端末の中の列は1つも減っていません。 「対策しました」と言うかわりに「このマスがこう動きました」と言えると、その主張は相手が検証できる形になります。

ついでに、列が完全に消える対策のほうが珍しいことにも気づいてほしいところです。 多くの対策は、攻撃に必要な前提を1つ増やすだけです。 第4章の「認証つきの鍵」がその典型で、プロセス内の ● は消えず、◐ になります。

2つ目。消えずに残った列が、そのまま報告書に書く残存リスクです。 報告書の価値は、見つけた脆弱性の数ではなく、どこまで見て、どこから先は見ていないのかが読み手に分かることにあります。 この表は、埋めたマスと埋めていないマスが同じ形で残るので、そのまま範囲の申告になります。 第3章の adb shell や root の行に 未検証 が付いているのは、そのためです。 そのマスは「届かない」ではなく「まだ何も言えない」です。

3つ目。次に別のアプリを見るときは、章ではなくこの表を先に書いてください。 資産を縦に並べ、立場を横に並べ、埋まらないマスを潰していく。 その順番で進めるかぎり、教材に出てこなかった構成でも同じやり方が使えます。
